# 여백 개편 기획서

> 초기 31개 노트를 개편할 때 작성한 기록입니다. 현재 작업 기준은 [AGENTS.md](../../AGENTS.md), 다음 글의 범위는 [콘텐츠 계획](../content-plan.md)에서 확인합니다.

## 1. 목적과 방향

여백은 프론트엔드 개발 과정에서 마주친 문제와 선택의 이유를 공유하는 개인 기술 기록이다. 브라우저의 기본 동작에서 실제 라이브러리·개발 도구·서비스를 설계하고 운영하기까지 이어지는 판단을 하나의 흐름으로 정리한다.

독자는 프론트엔드 기본기를 익혔거나 실제 제품을 구축 중인 개발자다. 첫 방문에서 자신에게 필요한 장을 찾고, 해당 장의 한 글에서 문제의 원인과 구현 구조를 이해하여 자신의 코드에 적용할 판단 기준을 얻는 것이 목표다.

현재 31개 노트는 개념별로 분리되어 있어 동일한 문제의 원인, 코드, 검증, 후속 개선이 떨어져 있다. 개념 설명 뒤에 단편적인 사례를 붙이는 방식은 중단한다. 실제 이슈·PR·커밋을 먼저 조사하고 그 사례를 해설하기 위해 필요한 기초 개념을 글 안에 배치한다. 긴 글을 억지로 여러 편으로 쪼개지 않으며 독립적인 책임이나 재사용 가치가 있을 때만 문서를 나눈다.

## 3. 글 설계 원칙

한 글은 하나의 기술적 질문을 끝까지 다룬다. 모든 글에 동일한 긴 템플릿을 강제하지는 않되 사례 중심 글에는 다음 책임을 포함한다.

1. 왜 문제인지: 사용자 행동, 기존 구현, 관찰한 버그나 요구사항, 실제 근거.
2. 어떻게 동작하는지: 브라우저·프레임워크·상태·데이터 계약, 관련 코드와 필요한 기초 개념.
3. 어떻게 설계하는지: 상태/모듈의 소유권, 데이터 흐름, 핵심 경계, 실패 및 복구, 대안 비교.
4. 어떻게 구현했는지: 독립적으로 재현 가능한 핵심 예제, 코드 설명, 필요할 때 상태 전이 또는 구조도. 실제 구현과 설명용 예제를 명시적으로 구분한다.
5. 어떻게 검증했는지: 입력·폭·환경·브라우저·경계 조건, 이전 실패와 기대 동작, 실제 확인 결과와 검증하지 못한 항목.
6. 무엇을 일반화할지: 선택의 단점, 적용하지 말아야 할 상황, 관련 후속 글, 공식 문서와 이슈·PR·커밋.

짧은 기본 개념은 1~2개의 실전 질문을 해결하는 하나의 읽기 단위로 묶는다. 복잡한 사례는 본문에서 구조와 동작을 충분히 해설하고, 단순한 체크리스트나 요약이 본문을 대체하지 않도록 한다. 분량은 강제하지 않되 깊은 사례 연구는 코드, 실패 비교, 검증 사례를 갖춰야 한다. 사용자가 실제로 설명할 수 없는 구현 상세, AI가 수행했다는 이유만으로 작성자의 경험으로 단정하는 서술은 금지한다.

### 사례 근거와 공개 범위

- 공개 이슈는 요구사항과 당시 고민의 근거다. 닫힌 이슈도 완성 여부는 연결된 병합 PR, 실제 리비전, 테스트 및 공개 릴리스를 확인한다.
- 공개 PR과 커밋은 구현의 근거다. 검증은 실제 결과가 있는 경우에만 사실로 기록한다.
- 열린 이슈는 설계 후보로만 기록한다. 아직 구현된 기능이라고 서술하지 않는다.
- 회사 저장소에서 얻은 일반화 가능한 교훈은 독립적인 합성 예제로만 작성한다. 내부 코드, 고객 데이터, 파일 이름, 비공개 링크 및 운영 정보는 공개하지 않는다.
- React Fiber, V8, JIT, 브라우저 렌더링 엔진의 내부 구현, GPU 파이프라인, 셰이더, 고급 컴파일러 구현은 별도의 작성자 이해 확인이 필요한 후보로 유지한다. Boundra의 경계 검사나 Vertactics의 3D 화면을 사용했다고 해당 엔진 구현을 알고 있다고 판단하지 않는다.

## 4. 문서 경험 설계

- 랜딩: 한 문장으로 목적 설명, 주요 장으로 바로 이동, 대표 글 2~3개의 제목과 해결하는 실제 문제를 노출한다. 기능 소개나 실험실 홍보를 별도로 두지 않는다.
- 장 소개: 학습 순서를 제안하고 장의 관점에서 해결할 질문과 연관된 실제 사례를 묶는다.
- 본문: 명확한 제목·절 계층, 읽기 쉬운 줄 길이, 설정·출력·코드·결과를 가까이 배치한다. 코드가 길면 핵심 부분만 먼저 보여주고 전체 예제로 연결한다.
- 탐색: 현재 장과 문서를 표시하는 사이드바, 현재 절의 목차, 검색, 이전/다음 문서를 제공한다. 프로젝트명·기술 키워드로도 찾을 수 있도록 본문과 메타데이터를 구성한다.
- 인터랙티브 예시: 단순 개념은 코드/도식으로 설명한다. 상태·레이아웃·포커스·드래그 같은 관찰 가능한 차이만 문서 안에서 직접 조작할 수 있게 설계한다. 별도 Storybook이나 실험 사이트를 추가하지 않는다.
- 모바일: 읽기 중심의 단일 열, 접을 수 있는 탐색, 명확한 코드 스크롤과 작은 폭에서도 터치·키보드 접근 가능한 조작부.
- 기존 URL은 보존한다. 글을 합치는 경우 명시적 호환 경로와 검색 결과 연결을 먼저 설계한 뒤 승인받아 변경한다.

## 5. 시각적 정체성과 로고

공책, 종이, 연필, 형광펜, 모눈 등의 콘셉트는 사용하지 않는다. 여백을 넉넉하게 활용하는 미니멀한 기술 아카이브를 구축한다. 현대적인 산세리프, 중립적인 흑백 명암, 가독성이 높은 코드와 텍스트, 단순한 그리드 및 분명한 읽기 순서를 우선한다.

| 역할 | 밝은 테마 | 어두운 테마 |
| --- | --- | --- |
| 배경 | #FFFFFF | #111113 |
| 보조 표면 | #F7F7F8 | #19191C |
| 본문 | #18181B | #F4F4F5 |
| 보조 텍스트 | #52525B | #A1A1AA |
| 구분선 | #E4E4E7 | #303036 |
| 포커스 | #2563EB | #93C5FD |
| 오류 | #B91C1C | #FCA5A5 |

홈의 핵심은 글 탐색이며 대표 글에 실제 문제를 소개하고 목차로 연결한다. 본문은 독자의 읽기 길이, 코드, 표, 예제의 대비에 집중한다. 선택 상태는 명암과 표시 형태로 분명히 구분한다. 모션은 사용자의 입력을 확인하는 짧은 상태 전환에 한정하며 초기 문장을 움직이거나 숨기지 않는다.

로고는 별도 결정으로 보류한다. 기존 로고, 파비콘 및 브랜드 벡터는 유지하며 이 개편에서 교체하지 않는다.

### 모션과 접근성

기존의 절제된 모션 원칙을 유지한다. 실제 상태 또는 데이터 변화에 해당하는 데모는 결과와 원인을 보여주되 반복 모션에 독자의 읽기 흐름을 맡기지 않는다. 키보드 접근, 포커스 유지, 줄바꿈, 작은 화면, 다크 테마, 모션 감소 환경을 함께 검증한다.

## 6. 구현 승인 이후 단계

| 단계 | 완료 조건 |

| 2. 문서 UI 개편 | 중립색, 타이포그래피, 목차·검색·인라인 예제 검증. 로고는 별도 보류 |
| 3. 대표 사례 작성 | Juliya·Oddmash UI·Boundra·Foloom의 핵심 글을 먼저 작성하고 글의 깊이와 설명 방식을 검토 |
| 4. 기존 글 통합 | 31개 글을 재구성하고 관련 글/기존 경로 호환을 확인 |

| 6. 사이트·README 반영 | 승인된 목차와 실제 공개된 경로, 문서 UI 변경. 로고는 별도 승인 시 반영 |
| 7. 검증·배포 | 타입·린트·빌드, 문서 경로/검색, 예제 조작, 320px/375px/데스크톱, 테마, 모션 감소, Juliya 적용, 실제 Pages URL 확인 |

기술 스택은 Astro Starlight와 필요한 React 인라인 예제를 유지한다. pnpm, SCSS, 기존 src/ 절대 경로, 파일 케밥 케이스 규칙을 보존한다. 구조나 프레임워크 변경은 실제 필요가 확인되지 않으면 하지 않는다.

이번 변경은 문서 UI와 기존 31개 글의 탐색 구조에 한정한다. 신규 기술 글의 집필 및 로고는 추후 별도로 진행한다.
