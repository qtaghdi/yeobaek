사용자가 저장 버튼을 클릭했는데 화면이 그대로라면 요청이 진행 중인지 실패했는지 알 수 없습니다. 반대로 모든 일을 알림으로 띄우면 중요한 정보가 묻힙니다.

## 상태별 책임

| 상태 | 표시할 정보 |
| --- | --- |
| 진행 중 | 어떤 행동이 진행 중인지 |
| 성공 | 무엇이 완료되었는지 |
| 실패 | 무엇이 잘못됐는지, 다음 행동은 무엇인지 |
| 빈 상태 | 결과가 없는 이유와 가능한 행동 |

버튼 자체가 변경되는 경우 텍스트와 폭을 고려합니다. 짧은 성공 피드백은 버튼과 가까이 표시할 수 있고, 전체 작업에 영향을 주는 오류는 눈에 띄는 위치에 둡니다.

## 접근성과 복구

상태가 비동기적으로 변할 때 필요에 따라 정중한 알림 영역을 사용합니다. 오류 메시지는 해당 입력과 연결하고, 다시 시도할 수 있도록 합니다. 지나치게 많은 토스트를 겹쳐 띄우거나 포커스를 강제로 옮기지 않습니다.

[W3C: Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)

## 프로젝트에서 이어진 고민

Toast의 성공 메시지와 긴급 오류를 같은 방식으로 알리면 과도한 알림이 발생할 수 있다. 이슈에서는 status와 alert의 역할, 닫힌 알림을 다시 읽지 않는 조건, 키보드로 닫는 동작을 구분했다.

### 검증 기준

복사 성공처럼 일반적인 결과는 정중한 알림으로, 즉시 주의가 필요한 오류는 상황에 맞는 알림으로 전달한다. 실제 비동기 결과를 받은 뒤 성공을 표시하며 실패 시 다시 시도할 수 있게 한다.
