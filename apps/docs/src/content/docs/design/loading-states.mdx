원본 화면을 예상하지 않은 작은 로딩 표시와 실제 카드 크기에 맞춘 스켈레톤을 비교합니다. 동일한 영역에서 로딩 완료 버튼을 눌러 요소의 위치가 얼마나 움직이는지 살펴보세요.

## 로딩 전후의 기하 구조

스켈레톤은 데이터를 기다리는 동안 보이는 콘텐츠의 형태를 예상할 수 있게 해 줍니다. 그 자체가 레이아웃의 문제를 해결하지는 않습니다. 첫 사례에서는 로딩 표시의 높이가 작고 완료 뒤 카드가 커지면서 뒤의 내용이 밀립니다. 두 번째 사례에서는 완료된 카드와 같은 최소 높이와 배치를 유지합니다.

실제 레이아웃의 변화는 높이뿐 아니라 콘텐츠의 폭이 달라져 텍스트가 추가로 줄바꿈되거나, 이미지의 고유 크기가 늦게 결정되면서도 발생합니다.

```css
.card {
  min-block-size: 8rem;
  display: grid;
  align-content: start;
  gap: .75rem;
}
```

카드 자체의 구조를 공유하고 로딩일 때 내부 콘텐츠만 대체하면 서로 다른 카드 두 개를 관리할 때 발생하는 크기 편차를 줄일 수 있습니다. 화면의 데이터 길이를 정확히 예상할 수 없다면 고정 높이로 문장을 잘라내기보다 최소 높이를 확보하는 것으로 시작합니다.

## 최초 로딩과 이미 표시된 데이터의 갱신

| 상태 | 표시할 UI |
| --- | --- |
| 처음 진입, 데이터 없음 | 실제 레이아웃을 예고하는 스켈레톤 |
| 이전 데이터가 있고 갱신 중 | 기존 내용 유지와 갱신 피드백 |
| 조회 결과 없음 | 실제 빈 상태와 필요한 다음 행동 |
| 실패 | 재시도할 수 있는 오류 상태 |

필터를 새로 적용했을 때 이전 결과를 계속 보여 줄지 비울지는 이전 결과를 새로운 조건의 것으로 오해할 위험과 읽기 흐름을 비교해서 선택합니다. 새 조건에 맞는 데이터가 아니라는 사실을 구분하지 않고 이전 결과를 그대로 표시하면 안 됩니다.

## 이미지의 로딩과 실패

[Vertactics #67](https://github.com/Oddmash/vertactics/issues/67)에서는 지도·영웅 초상화·카드의 실제 비동기 이미지에 대해 로딩과 실패 표현을 다뤘습니다. 이미지가 나중에 로드되더라도 배치 위치와 크기를 미리 확보해야 사용자가 목록을 안정적으로 탐색할 수 있습니다.

```css
.preview {
  aspect-ratio: 16 / 9;
  background: var(--surface);
}

.preview img {
  inline-size: 100%;
  block-size: 100%;
  object-fit: contain;
}
```

이 코드는 예시이며 모든 이미지에 16:9가 적합하다는 뜻은 아닙니다. 실제 자산의 비율과 필요한 표시 영역을 기준으로 geometry를 정합니다. 이미지를 실패했을 때 계속 로딩으로 표시하지 않고 같은 영역 안에 의미 있는 대체 상태를 제공합니다.

## 접근성과 모션

[Oddmash UI #39](https://github.com/Oddmash/oddmash-ui/issues/39)에서는 스켈레톤이 실제 콘텐츠로 해석되지 않도록 접근성 상태를 다뤘습니다. 아직 존재하지 않는 가짜 제목이나 목록 항목을 화면 읽기 도구에 노출하지 않습니다. 시각 장식은 aria-hidden으로 처리하고 필요한 로딩 상태를 독립적으로 전달합니다.

자동 반복 shimmer는 상태를 알기 위한 필수 요소가 아닙니다. 모션 감소 환경에서도 로딩과 완료가 분명해야 하며, 실패 이후 무한 로딩이 남지 않도록 실제 비동기 상태와 연결합니다.

## 검증 기준

- 같은 영역에서 로딩 전후의 다음 콘텐츠 위치를 비교합니다.
- 320px 화면과 긴 제목, 이미지 로딩 실패를 확인합니다.
- 갱신 중 이전 데이터를 표시하는 경우 적용 조건을 명확히 구분합니다.
- 완료·빈 결과·실패가 서로 다른 UI 상태로 표시됩니다.
- 접근성 트리에 가짜 콘텐츠나 불필요하게 반복되는 상태 알림이 노출되지 않습니다.
