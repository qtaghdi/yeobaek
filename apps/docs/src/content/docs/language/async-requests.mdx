## 먼저 보낸 요청이 먼저 도착한다는 보장이 없다

검색 조건을 A에서 B로 변경했을 때 A의 응답이 B보다 늦게 올 수 있습니다. 네트워크는 사용자의 조작 순서와 같은 순서를 보장하지 않습니다. 응답이 도착했다는 사실만으로 현재 화면을 변경할 권한이 생기는 것은 아닙니다.

| 시점 | 요청 A | 요청 B | 화면 |
| --- | --- | --- | --- |
| 1 | 시작 | 없음 | 로딩 |
| 2 | 진행 중 | 시작 | B 로딩 |
| 3 | 진행 중 | 완료 | B 결과 |
| 4 | 완료 | 완료 | B 결과 유지 |

마지막 순간에 A의 결과를 화면에 반영해버리면 사용자는 B를 선택했는데 A의 목록을 보게 됩니다. 화면을 변경할 수 있는 응답이 무엇인지를 정해야 하는 이유입니다.

## 직접 확인하기

동일한 두 요청에서 B가 먼저 완료하고 A가 늦게 도착하도록 고정한 합성 예제입니다. 왼쪽은 완료 순서대로 결과를 표시하고 오른쪽은 최신 요청의 결과만 반영합니다. 실제 서버에 요청하지 않습니다.

## 요청 생명주기

```ts
const controller = new AbortController();

const load = async () => {
  const response = await fetch("/api/items", {
    signal: controller.signal,
  });
  if (!response.ok) throw new Error("조회에 실패했습니다.");
  return response.json();
};

const cancel = () => controller.abort();
```

AbortController는 지원하는 작업을 취소할 수 있는 신호를 제공합니다. 기존 요청이 불필요해졌을 때 네트워크와 후속 처리를 중단하는 데 유용하지만, 모든 비동기 작업이 취소를 지원하는 것은 아닙니다. 서버에서 이미 완료한 쓰기 작업을 되돌리는 기능도 아닙니다.

## 완료된 결과도 현재 요청의 것인지 확인한다

다음은 요청마다 식별자를 부여해 최신 결과만 적용하는 설명용 예제입니다. 실제 API 응답의 구조는 validateItems에서 검사한다고 가정합니다.

```ts
let latest = 0;
let controller: AbortController | undefined;

const loadItems = async (query: string) => {
  const requestId = ++latest;
  controller?.abort();

  const current = new AbortController();
  controller = current;
  setStatus("loading");

  try {
    const response = await fetch(
      "/api/items?" + new URLSearchParams({ query }),
      { signal: current.signal },
    );
    if (!response.ok) throw new Error("요청 실패");
    const items = validateItems(await response.json());

    if (requestId !== latest || current.signal.aborted) return;
    setItems(items);
    setStatus("success");
  } catch {
    if (requestId !== latest || current.signal.aborted) return;
    setStatus("error");
  }
};
```

B가 먼저 완료된 뒤 A가 오류가 나더라도 현재 화면에 A의 오류를 띄우지 않습니다. 성공에만 최신 요청 조건을 걸고 오류나 finally에서 로딩 상태를 무조건 변경하는 일도 피합니다.

위 모델은 한 화면의 조회 작업을 설명한 것입니다. 여러 독립 조회가 있다면 각각의 키와 요청 생명주기를 관리해야 합니다. 컴포넌트가 사라질 때 요청을 중단하고 최신 ID를 무효화하는 정리도 필요합니다. 서버 상태 라이브러리는 이런 책임의 일부를 제공할 수 있으므로 공개 API를 확인합니다.

## 실제 복사 작업에서 나타난 같은 문제

Oddmash UI의 [#95](https://github.com/Oddmash/oddmash-ui/issues/95)에서도 완료된 Promise를 어디에 반영할지가 중요했습니다. ClipboardButton은 복사 동작에 pending 상태를 두고 요청 중에 콘텐츠가 바뀌면 처음 요청한 문자열과 현재 문자열을 비교합니다. 이전 문자열의 성공이 새로운 코드 예제의 복사 성공으로 표시되는 상황을 피하기 위해서입니다.

복사와 API 통신은 전혀 다른 기능처럼 보이지만, 이전 작업의 결과가 현재 상태를 덮어쓰지 않아야 한다는 점은 같습니다. 이 문제는 성공뿐 아니라 실패를 표시할 때도 똑같이 발생합니다.

## 실패와 재시도

| 상황 | 의미와 처리 |
| --- | --- |
| 다른 조건으로 이동한 요청을 취소 | 이전 상태의 실패로 알릴 필요 없음 |
| 네트워크 연결 실패 | 이전 데이터 유지 및 재시도 검토 |
| HTTP 비정상 응답 | 상태와 API 계약에 따른 오류 처리 |
| 정상 HTTP 응답이지만 데이터 불일치 | 런타임 검증 오류 |
| 상태를 변경하는 요청의 실패 | 재실행 가능 여부 및 중복 변경 확인 |

읽기 요청의 취소와 쓰기 요청의 복구 정책은 동일하지 않습니다. 저장 요청의 응답이 유실되었다고 서버에 저장되지 않았다는 뜻은 아닙니다. 다시 저장하기 전 성공 여부를 확인하거나 저장 작업에 중복을 식별할 수 있는 계약을 갖추는 이유입니다.

## 문서 저장에서 revision이 필요한 이유

Foloom의 [PR #31](https://github.com/qtaghdi/foloom/pull/31)은 파일 내용이 그대로인 저장이 revision과 undo 이력을 늘리고, 열린 편집 화면에 불필요한 충돌을 만드는 문제를 다룹니다.

문서가 revision 3일 때 내용이 동일한 저장을 반복하며 revision이 4로 바뀐다면 사용자가 다음 요청에서 revision 3을 보냈을 때 실제로 변경된 내용이 없는데도 이전 버전이라는 이유로 실패할 수 있습니다.

실제 수정은 저장할 결과의 바이트 해시가 기존 해시와 동일한 경우 현재 snapshot을 반환하며 revision과 두 history stack을 보존합니다. 이 경우 이전 undo뿐 아니라 이미 존재하던 redo도 그대로 남아야 합니다. 공개 테스트는 변경 후 undo를 실행한 상태에서 동일한 값을 다시 저장하여 revision과 redo, 파일 바이트가 보존되는지 확인합니다.

편집 브라우저도 원격 이벤트를 받을 때 값의 최신성 및 pending 편집 유무를 고려합니다. 해당 변경의 브라우저 컨트롤러는 유휴 상태에서 새 revision을 수신하면 snapshot과 history 상태를 동기화하도록 처리합니다. 동시에 로컬 편집이 진행 중인 경우는 무조건 덮어쓰지 않아야 합니다. 이 사례를 모든 협업 편집의 보편적인 병합 알고리즘으로 해석해서는 안 됩니다.

## 현재 화면은 누구의 결과를 보여줄까?

검색어를 바꾸는 것은 정상적인 사용자 행동입니다. 이전 요청이 취소됐다고 화면에 실패 알림까지 뜨면 오히려 사용자 입장에서는 이상합니다. 그렇다고 모든 오류를 무시하면 지금 요청이 정말 실패했을 때 재시도할 방법이 없어집니다.

A가 실패하고 B가 성공했는데 A의 오류가 나중에 도착한다면 B 결과를 그대로 보여줘야 합니다. 저장처럼 서버에 변경을 일으키는 요청은 조회와 달리 돌이키기 어려운 결과가 있으므로 요청 재전송과 중복 처리 계약까지 별도로 고민해야 합니다.
