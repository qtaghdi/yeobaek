모달의 배경 스크롤을 막았을 뿐인데 헤더와 본문이 좌우로 움직입니다. 모달 애니메이션의 문제처럼 보이지만 사실 스크롤바가 차지하던 폭이 사라지면서 생기는 변화일 수 있습니다.

## 사라진 스크롤바의 폭

전통적인 스크롤바는 콘텐츠 영역의 일부 폭을 차지합니다. 스크롤 잠금으로 스크롤바가 사라지면 사용 가능한 폭이 달라집니다. `100vw`로 지정한 래퍼가 일반적인 사용 가능한 콘텐츠 폭과 다를 수 있는 것도 원인입니다.

예를 들어 320px 뷰포트에서 클래식 스크롤바가 15px를 차지하면 콘텐츠가 사용할 수 있는 너비는 305px입니다. 모달이 열리면서 스크롤바가 사라지면 그 공간이 다시 콘텐츠로 돌아갑니다. 중앙에 배치한 요소가 옆으로 움직이는 이유입니다.

## 공간을 남겨두는 방법

```css
html {
  scrollbar-gutter: stable;
}
main {
  inline-size: 100%;
}
```

`scrollbar-gutter: stable`은 고전적인 스크롤바가 차지할 공간을 안정적으로 유지하는 방법입니다. 오버레이 방식의 스크롤바는 별도의 공간을 차지하지 않을 수 있습니다.

스크롤 잠금 자체도 올바른 요소에 적용하고 모달 안의 콘텐츠가 넘칠 때 별도 스크롤이 가능한지 확인합니다. 고정 헤더와 sticky 요소까지 포함해 모달을 열기 전후의 폭을 비교하면 원인을 좁히기 쉽습니다.

[MDN: scrollbar-gutter](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/scrollbar-gutter)

## 작은 화면에서 유독 잘 보이는 이유

[Oddmash UI #81](https://github.com/Oddmash/oddmash-ui/issues/81)을 살펴보면 앞에서 설명한 문제가 실제로 어떻게 나타나는지 알 수 있습니다. 320px 화면에 15px 스크롤바가 표시되면 사용할 수 있는 공간은 305px이 됩니다. 그 안에서 288px Toast의 좌우 여백이 각각 1px과 16px이라면 화면 중앙에 있는 것처럼 보이지 않겠죠.

운영체제에 따라 스크롤바가 차지하는 너비도 달라지므로 고정된 뷰포트 숫자보다 실제 콘텐츠 영역을 기준으로 배치하는 것이 중요합니다.

<span id="320px이-항상-320px은-아니다"></span>

```css
:root {
  scrollbar-gutter: stable;
}
.toast-region {
  max-inline-size: calc(100% - 2rem);
  margin-inline: auto;
}
```

`scrollbar-gutter`로 공간을 남겨두고 Toast의 최대 너비를 실제 컨테이너에서 계산할 수 있습니다. 다만 Toast가 어떤 containing block을 기준으로 배치되는지에 따라 결과가 달라집니다. 스크롤바가 표시되는 환경과 오버레이 방식인 환경에서 각각 잠금 전후를 비교하면 어떤 부분이 어긋나는지 찾기 쉽습니다.
