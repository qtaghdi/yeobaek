프론트엔드를 개발한다면 CSR과 SSR이라는 말을 한 번쯤 들어봤을 겁니다. 어디에선 SSR이 좋다고 하고 어디에선 CSR이 좋다고 하니 처음에는 헷갈릴 수 있습니다.

둘 중 하나가 무조건 더 좋은 전략이라면 이렇게 고민할 필요도 없겠죠. 화면을 만드는 시점과 필요한 데이터가 무엇인지부터 살펴보면 차이를 이해하기 쉽습니다.

## HTML을 브라우저에서 만들까, 서버에서 만들까?

CSR에서는 브라우저가 JavaScript를 실행해 화면을 구성합니다. Vite로 만든 일반적인 React SPA를 생각해보면 쉽습니다. 초기 HTML은 간단한 컨테이너이고 JavaScript가 준비되면서 실제 화면이 나타납니다.

서버가 HTML을 만드는 SSR에서는 요청을 받아 데이터를 준비하고 HTML을 반환합니다. 브라우저는 받은 HTML을 표시할 수 있지만 React의 인터랙션을 붙이려면 클라이언트 코드가 준비되어야 하는 경우가 있습니다.

여기서 주의할 점은 처음 보이는 화면과 실제로 조작할 수 있는 화면의 시점이 다를 수 있다는 것입니다. SSR을 선택했다고 JavaScript 실행 비용이 자동으로 사라지지는 않습니다.

## 페이지가 거의 바뀌지 않는다면?

기술 문서처럼 내용이 배포하기 전까지 바뀌지 않는다면 요청마다 HTML을 생성할 필요가 있을까요?

SSG는 빌드 시점에 HTML을 미리 만듭니다. 여백처럼 정적 문서를 배포하는 사이트에서는 요청마다 서버가 같은 글을 다시 생성하지 않아도 됩니다. 하지만 페이지 내용이 바뀌면 다시 빌드하거나 별도의 갱신 방식이 필요합니다.

ISR은 프레임워크와 배포 환경이 지원할 때 정적 결과를 일정 조건에 따라 갱신할 수 있게 해줍니다. 캐시된 결과가 존재한다는 것과 가장 최신 자료가 표시된다는 것은 다릅니다. 상품 목록처럼 일정 시간 오래된 데이터를 제공해도 괜찮은 페이지라면 고려해볼 만하지만, 즉시 변경 사항이 반영되어야 하는 화면에 같은 정책을 그대로 적용하기는 어렵습니다.

## 페이지 하나가 느린 API 하나 때문에 멈춘다면?

헤더와 상품명은 이미 준비됐는데 리뷰 API 하나가 느립니다. 모든 데이터가 준비될 때까지 HTML 전송을 기다리면 나머지 영역도 늦게 보입니다.

Streaming은 준비된 부분을 먼저 보내고 느린 부분은 이후에 전달할 수 있게 합니다. React에서는 Suspense 경계가 이런 구성을 만드는 데 사용됩니다.

```tsx
const ProductPage = () => (
  <main>
    <ProductSummary />
    <Suspense fallback={<ReviewSkeleton />}>
      <Reviews />
    </Suspense>
  </main>
);
```

물론 위 구조만으로 모든 데이터 호출이 자동으로 스트리밍되는 것은 아닙니다. 프레임워크와 데이터 로딩 방식이 지원해야 합니다. 스켈레톤과 실제 리뷰 영역의 크기가 크게 다르면 사용자가 느끼는 화면 품질도 낮아질 수 있습니다.

## Server Component는 SSR이랑 같은 말일까?

React Server Components는 컴포넌트를 어떤 실행 환경에서 처리하는지에 관한 모델입니다. 서버 컴포넌트의 JavaScript를 브라우저 번들에 그대로 포함할 필요가 없도록 할 수 있습니다. 상태 변경과 이벤트 핸들러처럼 브라우저에서 실행할 코드가 있다면 클라이언트 컴포넌트가 필요합니다.

SSR은 HTML을 생성하는 위치와 시점에 관한 개념이고 RSC는 컴포넌트의 실행 경계에 관한 개념이므로 서로를 대체하지 않습니다.

## 그래서 무슨 전략을 고르면 될까?

| 요구 | 먼저 생각해볼 전략 |
| --- | --- |
| 정적 기술 문서 | SSG |
| 사용자별로 달라지는 요청 결과 | SSR 또는 클라이언트 조회 |
| 일정 주기로 바뀌는 공개 목록 | 정적 생성 및 갱신 |
| 여러 영역의 데이터 준비 시간이 다름 | Streaming |
| 일부 영역만 인터랙션이 필요함 | 서버와 클라이언트 실행 경계 분리 |

실제 성능은 데이터 처리 시간, 번들 크기, 네트워크, 캐시 여부에 따라 달라집니다. CSR도 초기 로드가 끝난 이후 서버 데이터를 받아 화면을 빠르게 변경할 수 있고, SSR도 서버가 느리면 첫 응답이 지연될 수 있습니다.

렌더링 방식의 이름을 외우는 것보다 내가 만드는 페이지에서 언제 어떤 정보가 필요한지를 먼저 고민해보면 좋겠습니다.
