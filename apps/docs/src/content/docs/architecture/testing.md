---

컴포넌트가 화면에 렌더링된다는 테스트만 통과해도 실제 키보드 조작이나 모달 닫기 동작이 깨질 수 있습니다. 무엇을 보장하고 싶은지에 따라 테스트를 나눕니다.

## 선택 기준

| 수준 | 확인할 문제 |
| --- | --- |
| 단위 테스트 | 입력값, 유틸리티, 계산 결과 |
| 컴포넌트 테스트 | 사용자 입력에 따른 상태와 화면 |
| 브라우저 테스트 | 실제 포커스, 레이아웃, 네비게이션 |
| 시각 회귀 | 스타일이나 배치의 예상치 못한 변화 |

예를 들어 모달 테스트에서는 열림 여부뿐 아니라 Escape로 닫히는지, 닫힌 후 포커스가 돌아오는지 확인합니다. 실제 사용자에게 노출되는 역할과 이름으로 요소를 찾으면 마크업 내부 구조에 과도하게 의존하지 않을 수 있습니다.

## 자동 검사의 한계

접근성 검사 도구가 발견하지 못하는 문제도 존재합니다. 자동 검사 결과와 실제 키보드 조작을 구분하고 모바일이나 다른 브라우저에서의 차이도 확인합니다.

[Testing Library: Guiding Principles](https://testing-library.com/docs/guiding-principles/) · [Playwright: Best Practices](https://playwright.dev/docs/best-practices)

## 프로젝트에서 이어진 고민

증분 스캔의 성능을 개선하기 전 전체 스캔과 결과가 일치해야 한다는 요구가 있었다. 빠르게 동작하더라도 놓친 진단이 있으면 개선이라고 할 수 없다.

### 검증 기준

동일한 fixture에서 전체 검사와 변경 후 증분 검사의 진단을 비교한다. 정확성 테스트를 먼저 만들고 이후 시간과 메모리 측정을 별도로 진행한다. 정상뿐 아니라 파일 추가·수정·삭제를 포함한다.

[관련 이슈 · boundra #142](https://github.com/Oddmash/boundra/issues/142)

## 먼저 참조 결과를 만들고 최적화한다

Boundra에서 [증분 스캔의 결과 일치](https://github.com/Oddmash/boundra/issues/142)를 검토한 이유는 성능 향상이 정확성 저하를 숨길 수 있기 때문이다. 전체 스캔은 시간이 더 걸리더라도 비교 기준이 된다.

| 변경 | 비교할 결과 |
| --- | --- |
| 파일 추가 | 새 진단이 양쪽에서 나타남 |
| import 수정 | 이전 진단이 사라지거나 새 진단이 생김 |
| 파일 삭제 | 삭제된 경로의 오래된 진단이 제거됨 |
| 동일 입력 | 결과가 변하지 않음 |

테스트는 통과 개수가 아니라 지키려는 계약으로 설계한다. 최적화된 구현과 기준 구현의 출력이 같다는 사실을 먼저 확인하고, 동일한 환경과 입력으로 실행 시간을 측정한다. 빠른 결과가 틀린 결과라면 사용자는 검증 도구를 신뢰할 수 없다.
