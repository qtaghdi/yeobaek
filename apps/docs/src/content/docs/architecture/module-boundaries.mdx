## 폴더가 깔끔하면 좋은 구조일까요?

폴더를 기능별로 나누는 목적은 코드를 예쁘게 정리하는 것이 아닙니다. 어떤 변경을 어디서 관리해야 하는지와 어떤 코드가 다른 코드를 알아도 되는지를 명확하게 하기 위한 것입니다. 보기에는 잘 정리된 폴더라도 모든 모듈이 서로의 내부 구현을 자유롭게 import할 수 있다면 경계가 존재한다고 보기 어렵습니다.

## 같이 바뀌는 코드를 가까이

```text
src/
  orders/
    order-list.tsx
    use-orders.ts
    order-types.ts
  shared/
    ui/
    api/
```

특정 기능에서만 쓰는 코드는 해당 기능 근처에 두고 실제 여러 기능이 공유하는 것은 공용 영역으로 옮깁니다. 모든 폴더에 components, hooks, utils를 미리 만드는 대신 변경이 함께 발생하는 위치를 기준으로 정리합니다.

공통화와 공개는 다른 결정입니다. 단일 모듈 안의 함수는 다른 내부 함수에서 공통으로 사용할 수 있지만, 다른 도메인이 그 함수의 구현까지 알아야 한다는 뜻은 아닙니다.

## 어디까지 공통으로 만들까

다른 기능이 주문 상태를 조회해야 한다고 가정해 보겠습니다.

```ts
import { getOrderStatus } from "src/orders/internal/status-store";
```

이 방식은 소비자가 내부 저장 구조에 의존하게 만들 수 있습니다. 공개 진입점의 계약을 먼저 정의하고 내부 구현을 숨길 수 있다면 변경 영향이 줄어듭니다.

```ts
import { getOrderStatus } from "src/orders/public";
```

폴더 이름 public 자체에는 특별한 힘이 없습니다. 실제 export와 의존 방향, 타입 계약이 그 의미를 만들어야 합니다. 위 코드는 설명을 위한 독립 예시이며 모든 프로젝트에 같은 구조를 강제하지 않습니다.

## 경계를 자동으로 검증할 때

[Boundra](https://github.com/Oddmash/boundra)는 프로젝트의 구조와 import를 분석하고 선언된 경계 규칙에 위반되는 관계를 진단합니다.

경계 검사를 만들 때에는 단순히 import 문자열에 특정 단어가 있는지 확인하는 것만으로 충분하지 않습니다. 상대 경로, tsconfig와 패키지 alias, 모듈의 실제 위치가 서로 영향을 줍니다. 같은 문자열이라도 다른 설정에서 다른 모듈을 가리킬 수 있습니다.

[Boundra #43](https://github.com/Oddmash/boundra/issues/43)에서는 실제 Next.js App Router와 Vite TypeScript 소비자 fixture를 추가하는 방향을 검토했습니다. 프레임워크별 예제를 따로 만들더라도 규칙의 의미와 공개 진단의 형식은 공통으로 유지할 필요가 있습니다.

| 구성 | 책임 |
| --- | --- |
| 프로젝트 모델 | 도메인·경로·설정·별칭의 해석 |
| import 수집 | 실제 분석 대상과 import 정보 수집 |
| 규칙 평가 | 선언된 경계와 관계 비교 |
| 진단 | 규칙, 경로, 위치와 이유 전달 |
| CLI·에디터 | 사용자 입력과 표시·출력의 책임 |

Boundra의 실제 코드는 다양한 Rust crate와 통합 어댑터를 사용합니다. 여기서는 프론트엔드 아키텍처에 적용할 수 있는 책임 분리를 설명하며 컴파일러 내부 구현은 다루지 않습니다.

## 변경 파일만 보고할 때 주의할 점

[Boundra #158](https://github.com/Oddmash/boundra/issues/158)의 변경 파일 검사 설계에서 중요한 부분은 검사 범위를 줄이는 것과 사용자에게 보고할 범위를 좁히는 것을 구분하는 것입니다.

예를 들어 변경된 파일 A가 새로운 위반을 만들었고, 변경되지 않은 파일 B에 기존 위반이 있다고 가정합니다. B를 제외하고 검사하면 실제 프로젝트의 상태와 다른 결과가 됩니다. 전체 모델을 검사한 뒤 A와 관련된 진단을 focused, 나머지를 other로 구분하면 변경에 집중하면서도 전체 상태를 잃지 않습니다.

```sh
boundra check-changed --base HEAD --format=json
```

이는 실제 CLI의 명령 계약입니다. 변경 파일의 추가·삭제·이름 변경, alias와 설정 변경을 처리하지 못하는 상황에서는 전체 검사로 돌아갈 필요가 있습니다. 실제 공개 테스트에는 새 파일·staged 변경·삭제와 기존 진단을 함께 검증하는 fixture가 있습니다.

## 기존 위반을 단계적으로 개선하기

레거시 프로젝트에 규칙을 도입할 때 모든 기존 위반을 한 번에 수정해야 한다면 도구를 쓰기가 어렵습니다. [Boundra #157](https://github.com/Oddmash/boundra/issues/157)에서 다루는 baseline은 현재 위반 상태를 명시적으로 기록하고 새로운 위반을 구분하려는 접근입니다.

```sh
boundra baseline create
boundra baseline check --baseline baseline.json
```

첫 명령은 versioned JSON 결과를 출력합니다. 실제 저장 위치는 사용자가 정해야 하며, 두 번째 명령은 특정 baseline을 비교 대상으로 사용합니다. 기존 일반 경계 검사는 baseline을 자동으로 적용하지 않습니다.

baseline은 위반을 영구적으로 숨기는 설정이 아닙니다. 기존·신규·해결된 위반을 구분하고, 기준 비교가 가능한 충분한 검사 범위를 유지하는 것이 목적입니다. 진단의 식별자, 이름 변경과 중복, 설정 변경의 영향을 검증하지 않으면 잘못된 이전 상태를 정상으로 오해할 수 있습니다.

## 폴더 이름이 아니라 변경의 책임을 나눈다

예전에 역할별 폴더에서 블로그 등록 UI를 수정하려고 components, queries, hooks, types를 차례로 열어야 했습니다. FSD를 도입하고 기능 가까이 관련 코드를 두니 어디를 봐야 할지 훨씬 명확해졌습니다. 다만 모든 프로젝트를 정해진 FSD 레이어에 맞출 필요는 없습니다.

Boundra로 구조를 검사할 때도 같은 생각을 적용했습니다. 단순한 폴더 규칙을 늘리기보다 실제 import 관계를 확인하고 이전에 있던 위반과 새 위반을 구분해야 합니다. 변경 파일만 보고할 때 전체 검사가 성공했다는 의미로 해석되지 않아야 하는 것도 중요합니다.

이 글은 벨로그의 [당신이 FSD 구조를 써야 하는 이유](https://velog.io/@qtaghdi/당신이-FSD-구조를-써야-하는-이유)를 바탕으로 기능 중심 구조와 모듈 경계까지 다시 정리했습니다.
