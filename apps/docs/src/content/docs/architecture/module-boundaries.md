description: "기능별 코드 배치와 공개 인터페이스."
---

프로젝트를 처음 만들 때는 components, hooks, utils 같은 기술별 폴더가 편합니다. 기능이 많아지면 특정 화면의 수정이 여러 폴더로 흩어질 수 있습니다.

## 같이 바뀌는 코드를 가까이

```text
src/
  app/
    orders/
      page.tsx
      _components/
      _hooks/
      _utils/
  shared/
    ui/
    api/
```

라우트에서만 사용하는 코드는 해당 라우트 가까이에 두고, 실제로 여러 기능이 공유하는 것은 공통 영역으로 분리합니다. 프레임워크가 제공하는 특별한 폴더 규칙은 따로 확인합니다.

## 어디까지 공통으로 만들까

다른 기능의 내부 구현을 직접 가져오면 변경 영향이 커집니다. 필요한 공개 함수와 타입을 정해 의존 방향을 분명히 합니다. 모든 프로젝트에 동일한 폴더 구조를 강제할 필요는 없습니다.

모듈 경계를 자동으로 확인하는 접근을 살펴볼 수 있는 프로젝트가 [Boundra](https://github.com/Oddmash/boundra)입니다. 도구를 사용하더라도 먼저 어떤 의존을 허용할지 결정해야 합니다.
