탭 키를 계속 눌러 폼을 채우다가 갑자기 화면 위로 포커스가 뛰어간다면 어떨까요? 마우스로는 아무 문제 없어 보이던 레이아웃도 DOM 순서와 시각적 순서가 다르면 키보드 사용자에게 꽤 불편합니다.

## 숫자를 붙이면 해결될까요?

| 값 | 동작 |
| --- | --- |
| 기본 | 버튼, 링크, 입력 등은 브라우저가 정한 기본 순서에 참여 |
| 0 | 일반적인 순차 포커스 탐색에 참여 |
| -1 | 순차 탐색은 제외하지만 코드로 포커스 가능 |
| 양수 | 양수 그룹 안에서 값 순서로 우선 탐색 |

양수 값을 여러 곳에 주면 나중에 UI가 삽입될 때 전체 탐색 순서를 관리해야 합니다. 가능한 한 자연스러운 DOM 순서와 기본 HTML 요소를 사용합니다.

예를 들어 카드 A, B, C가 DOM에 순서대로 있는 상태에서 CSS로 C를 가장 앞에 배치하더라도 Tab 순서는 자동으로 C부터 시작하지 않습니다. 양수 tabindex로 순서를 억지로 맞추면 다른 필드가 추가될 때마다 숫자까지 관리해야 합니다. 처음부터 읽는 순서에 맞게 DOM을 구성하는 편이 훨씬 단순합니다.

## Tab으로 순서를 비교해봅시다

일반 순서와 두 번째 버튼에 -1을 적용한 상태를 전환한 뒤, 예제 안으로 Tab을 이동해 보세요. 양수는 문서 전체의 탐색 순서에 영향을 줄 수 있으므로 이 예제에서는 적용하지 않습니다.

## CSS로 위치를 옮겼다고 순서까지 바뀌는 건 아니다

포커스 이동 순서를 바꾸는 것과 화면을 읽는 순서를 바꾸는 것은 다른 문제입니다. CSS `order`로 시각적 배치만 바꾼다고 DOM 순서가 바뀌는 것은 아닙니다. 커스텀 위젯에서 한 항목만 Tab 순서에 남기고 방향키로 이동시키는 패턴은 별도 키보드 처리가 필요합니다.

[MDN: tabindex](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/tabindex)

## 메뉴를 닫고 나면 어디에 있을까?

모바일 메뉴는 열기만큼 닫기도 중요합니다. [Oddmash UI #23](https://github.com/Oddmash/oddmash-ui/issues/23)에서 Escape로 메뉴를 닫는 문제를 다룬 이유도 여기에 있습니다. 닫힌 메뉴에 Tab이 들어가거나 현재 위치를 잃어버린다면 화면에서 메뉴가 사라졌다는 사실만으로는 부족합니다.
