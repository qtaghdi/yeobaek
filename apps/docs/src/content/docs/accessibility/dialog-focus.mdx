모달을 열고 내용까지 잘 표시했습니다. Escape로 닫히기도 합니다. 그런데 키보드로 열었던 사람은 과연 닫고 나서 어디로 가게 될까요? 모달의 상태는 isOpen 하나로 보이지만 사용자에게는 앞뒤의 조작 흐름이 연결되어 있습니다.

## 모달이 열린 동안 바뀌는 것

1. 트리거를 통해 열린다.
2. 모달 안의 적절한 요소에 포커스를 둔다.
3. 모달이 열린 동안 배경을 조작하지 않도록 한다.
4. 닫힌 뒤 가능한 한 기존 트리거에 포커스를 돌려준다.

실제 포커스 대상은 콘텐츠에 따라 다릅니다. 위험한 삭제를 확인하는 대화상자에서는 가장 안전한 행동이 적절할 수 있습니다. 긴 설명이라면 처음부터 읽을 수 있도록 제목이나 내용을 대상으로 잡는 것도 방법입니다.

예를 들어 상품 삭제 버튼을 누르고 확인 창을 열었다가 취소했다면 다시 그 상품의 삭제 버튼으로 돌아가는 것이 자연스럽습니다. 하지만 실제로 상품을 삭제했다면 버튼 자체가 없어질 수 있습니다. 그때는 주변 목록이나 제목처럼 계속 탐색할 수 있는 위치를 선택해야 합니다.

## 브라우저의 dialog를 써보면

```tsx
const dialog = useRef<HTMLDialogElement>(null);

<button onClick={() => dialog.current?.showModal()}>열기</button>
<dialog ref={dialog}>
  <p>내용을 확인하세요.</p>
  <form method="dialog">
    <button>닫기</button>
  </form>
</dialog>
```

`showModal()`로 연 네이티브 dialog는 모달의 배경 비활성화 등 기본 동작을 제공하지만, 알맞은 접근 가능한 이름과 초기 포커스는 여전히 설계해야 합니다.

## 키보드로 모달을 열어봅시다

시각 예제를 재생하면 Enter, Tab, Escape에 따라 포커스가 이동하는 순서를 볼 수 있습니다. 실제 브라우저 동작이 궁금하다면 아래 모달을 직접 열어보세요.

## 모달만의 문제는 아닙니다

여러 Toast 중 하나를 제거할 때도 비슷한 일이 생깁니다. 다른 알림이 남아 있는데 포커스를 원래 버튼으로 무조건 돌려버리면 계속 알림을 조작하던 흐름이 끊깁니다. [Oddmash UI #64](https://github.com/Oddmash/oddmash-ui/issues/64)처럼 닫힌 항목에 포커스가 있었을 때만 가까운 조작 가능한 요소로 옮기는 정책을 생각할 수 있습니다.
