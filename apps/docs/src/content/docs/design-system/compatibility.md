여러 프로젝트가 같은 컴포넌트를 사용하면 이름 하나를 바꾸는 작업도 다른 화면을 깨뜨릴 수 있습니다. 라이브러리 내부 구현과 공개 API를 구분하는 것이 중요합니다.

## 변경할 때 확인할 것

| 변경 | 확인할 영향 |
| --- | --- |
| Props 이름 | 호출하는 프로젝트의 컴파일 및 동작 |
| CSS 클래스·토큰 | 스타일을 덮어쓰는 사용처 |
| 이벤트·키보드 동작 | 기존 사용자 조작 및 접근성 |
| 패키지 내보내기 | 빌드, SSR 및 하위 경로 import |

이름을 바로 제거하기보다 이전 API의 대체 방법을 안내하고 필요하면 호환 기간을 둡니다. 제거할 때는 변경 내용과 마이그레이션 예시를 함께 제공합니다.

공개 API가 없는 내부 구현 수정과 사용자의 코드 수정을 요구하는 변경은 구분합니다. 버전 번호가 모든 호환성을 보증하지 않으므로 실제 소비 프로젝트에서 확인합니다.

[Semantic Versioning](https://semver.org/) · [Oddmash UI](https://github.com/Oddmash/oddmash-ui)

## 프로젝트에서 이어진 고민

프레임워크별 기능을 추가하기 전에 프레임워크와 무관한 공통 적합성 조건을 검증하는 방향이 논의되었다. 소비자 환경이 하나일 때 통과하는 API는 다른 빌드 도구의 해석 차이를 놓칠 수 있다.

### 검증 기준

공개 진입점, 타입, 오류, 기본 동작을 공통 계약으로 정한다. 실제 소비자 fixture에서 빌드하고 다른 프레임워크의 차이는 어댑터에 한정한다. 공개 계약 변경과 내부 구조 변경도 구분한다.
