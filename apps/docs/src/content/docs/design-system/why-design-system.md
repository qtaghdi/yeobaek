제가 UI 개발과 로직 개발을 함께 하던 시기에 여러 프로젝트를 오가다 보니 비슷한 버튼과 입력창을 다시 만드는 일이 많았습니다.

버튼이 필요하면 코드를 작성하고, 화면을 띄워보고, 스타일을 조금 수정합니다. 다른 프로젝트에 가면 또 버튼부터 작성합니다. 이걸 계속 반복하다 보니 이런 생각이 들었습니다.

"어차피 내가 다 만드는 건데 UI라도 한 번만 만들면 안 되나?"

거창한 이유로 디자인 시스템을 시작했던 건 아닙니다. 반복되는 일이 귀찮았고, 그 일을 줄이는 방법을 찾고 있었습니다.

## 디자인을 고정하는 시스템은 만들고 싶지 않았다

언젠가 디자이너가 합류하면 지금 제가 만든 UI는 전부 바뀔 수도 있습니다. 그렇다면 특정 디자인을 코드에 깊이 박아놓는 것보다는 동작과 표현을 분리하는 편이 좋겠다고 생각했습니다.

예를 들어 버튼이 빨간색인지 검은색인지보다 primary 행동을 표현하는 버튼인지가 더 중요합니다. 색상이 달라져도 버튼의 사용 방식과 접근성은 유지되어야 합니다.

그래서 [디자인 토큰](../tokens/)을 만들 때도 실제 필요해진 값을 중심으로 추가하는 방식을 선택했습니다. 앞으로 쓸지도 모르는 토큰을 미리 수십 개 만들어두면 정작 필요한 이름을 찾는 일이 더 어려워질 수 있습니다.

## 로컬에서 잘 보이는데 배포한 버전은?

컴포넌트를 npm 패키지로 제공하고 나면 소비자는 실제 UI를 어디서 확인할 수 있을까요? 코드와 타입만으로는 비활성화 상태나 테마, 포커스 링이 어떻게 생겼는지 파악하기 어렵습니다.

그래서 당시에는 Storybook에 컴포넌트의 상태별 예제를 정리하고 Chromatic으로 시각적 변화를 확인하는 방법을 고려했습니다. 패키지를 배포하는 것과 별개로 사용자에게 실제 화면을 보여줄 방법이 필요했기 때문입니다.

다만 Storybook이 디자인 시스템의 필수 조건이라고 생각하지는 않습니다. 여백에서도 문서 안에 인터랙션 예제를 넣는 방식으로 바꾸면서 별도의 Storybook을 없앴습니다. 사용하는 사람이 문서를 읽는 자리에서 결과를 볼 수 있다면 그 요구를 다른 방법으로도 충족할 수 있으니까요.

## 모든 프로젝트에 한 번에 도입해야 할까?

기존 앱 여러 개에 공통 컴포넌트가 도입돼 있지 않은 상황에서 전체를 한 번에 바꾸려면 새 컴포넌트를 만드는 작업보다 기존 화면을 수정하는 일이 더 커질 수 있습니다.

저는 신규 서비스나 우선순위가 높은 부분부터 차근차근 적용했습니다. 새 UI를 작성할 때 공통 컴포넌트를 가져오고, 기존 화면은 수정이 필요한 시점에 바꾸는 방식입니다.

이렇게 하면 디자인 시스템을 유지하는 비용과 각 앱을 유지하는 비용 사이의 균형도 잡을 수 있습니다.

## 디자인 시스템은 누구를 위해 만드는가

처음에는 제 시간을 아끼려고 시작한 일이었습니다. 그런데 필요한 정보를 문서에 남기고 컴포넌트 사용법을 일관되게 정리하다 보면 다른 사람이 같은 결정을 반복할 필요도 줄어듭니다.

버튼을 얼마나 많이 만들었는지보다 새로운 화면에서 버튼을 다시 설계해야 하는 일이 얼마나 줄었는지가 더 중요하다고 생각합니다.
