PR 검사의 이전 실행이 취소됐습니다. 같은 커밋에서 새로 시작한 실행은 통과했고 GitHub에도 초록색 체크가 떴습니다.

이제 리뷰가 시작되겠지 싶었는데, 에이전트는 여전히 CI를 기다리고 있습니다. 대체 어떤 검사를 보고 있었던 걸까요?

[Oddmash Agents의 PR #140](https://github.com/Oddmash/oddmash-agents/pull/140)에서 고친 문제입니다. 취소된 실행과 성공한 실행이 같은 커밋에 남아 있었습니다. 리뷰를 시작할 조건은 이미 갖춰졌는데, 에이전트가 이전 실행의 기록까지 현재 검사 결과로 보고 있었습니다.

## 같은 커밋에도 실행 기록은 여러 개 남습니다

예를 들어 PR의 최신 커밋이 `abc123`이고 같은 워크플로를 두 번 실행했다고 해보죠.

두 실행 중 어느 기록을 기준으로 리뷰를 시작해야 할지 먼저 생각해보세요. 둘의 커밋 값은 같습니다.

| 실행 | 커밋 | 결과 |
| --- | --- | --- |
| 125 | `abc123` | 취소 |
| 126 | `abc123` | 성공 |

여기서 126은 별도로 시작된 새 실행입니다. 기존 실행에서 `Re-run jobs`를 누르면 실행 번호는 그대로이고 시도 횟수만 올라갑니다. [GitHub Actions 기본 환경 변수](https://docs.github.com/en/actions/reference/workflows-and-actions/variables#default-environment-variables)

SHA로만 거르면 두 행이 모두 남습니다. SHA는 어떤 코드를 검사했는지 알려주지만, 그 코드를 검사한 실행이 몇 번째인지는 알려주지 않으니까요.

그럼 같은 이름의 검사 중 가장 최근에 끝난 하나만 보면 될까요? 비슷한 이름의 잡이 서로 다른 워크플로에 있을 수 있고, 이전 실행에서 늦게 도착한 기록이 최신 상태처럼 보일 수도 있습니다. 먼저 비교할 실행들을 같은 워크플로와 현재 PR에 속한 것으로 좁혀야 합니다. 그다음 실행 순서를 비교해야 어떤 기록이 이전 실행의 것인지 알 수 있습니다.

이 수정에서는 공개 PR에 대해 현재 헤드와 연결된 워크플로 실행을 확인합니다. 같은 워크플로의 더 새로운 실행이 이전에 취소된 실행을 대체한 것으로 확인되면, 이전 check suite의 기록을 현재 판단에서 제외합니다. 대신 새 실행의 check suite에 속한 검사 결과를 봅니다. 새 실행이 아직 진행 중이거나 필요한 최신 검사 결과를 확인할 수 없다면 리뷰를 보류합니다. [검사 결과를 판별하는 구현](https://github.com/Oddmash/oddmash-agents/blob/efc44d42fea19197f0808e45a1ec9d62799d973b/src/checks.ts)

## `/review`를 받는 동안 CI가 끝날 수도 있습니다

검사 결과를 제대로 해석해도 타이밍 문제가 하나 남습니다. 사람이 `/review`를 보낸 순간에는 검사가 진행 중인데, 에이전트가 대기 응답을 남기는 사이에 검사가 끝나는 경우입니다.

처음 조회한 상태를 응답 이후에도 그대로 쓰면, 검사가 끝났는데 리뷰 요청이 대기 상태에 남을 수 있습니다. 그래서 대기 응답을 남긴 뒤 검사 상태를 한 번 더 확인하도록 했습니다. 처음부터 필요한 검사가 모두 통과해 있다면 요청을 받았을 때 바로 시작합니다. 처음 조회와 대기 응답 사이에 결과가 바뀌었다면, 다시 확인한 결과로 판단합니다. [명시적 리뷰 요청 처리](https://github.com/Oddmash/oddmash-agents/blob/efc44d42fea19197f0808e45a1ec9d62799d973b/src/webhook-review.ts)

이 과정에서는 기다려야 하는 경우와 조치가 필요한 경우도 구분했습니다. 아직 실행 중이라면 완료를 기다릴 수 있지만, 필수 검사가 실패했거나 사용량 제한 때문에 실행되지 못했다면 기다리기만 해서는 상태가 바뀌지 않을 수 있습니다. 그 차이가 응답에 드러나야 요청한 사람이 다음 행동을 정할 수 있습니다.

## 초록색 체크 한 개로 충분할까?

실제 재현에는 [Oddmash UI #51](https://github.com/Oddmash/oddmash-ui/pull/51)의 검사 데이터를 사용했습니다. 같은 헤드에서 이전 구현이 리뷰를 막던 입력을 다시 넣어, 성공한 대체 실행을 기준으로 통과하는지 확인했습니다. 새 실행이 보류나 실패일 때 예전 성공을 가져와 통과시키는 일이 없어야 하므로, 그 경우도 테스트에 포함했습니다. [수정과 검증 기록](https://github.com/Oddmash/oddmash-agents/pull/140)

처음 봤던 초록색 체크로 다시 돌아가보죠. 이 문제를 고칠 때 확인해야 했던 건 체크의 색보다 **어떤 커밋의 몇 번째 실행이었는지**였습니다. 그래야 지금 시작해도 되는 리뷰인지 알 수 있으니까요.

## 기다림을 끝내기 위한 근거

커밋이 abc123인 검사에서 성공 상태를 발견했더라도 현재 PR이 이미 def456으로 갱신됐다면 같은 결과를 재사용할 수 없습니다. 반대로 같은 커밋의 이전 취소 실행을 계속 기다리면서 최신 실행의 완료를 놓치는 것도 문제가 됩니다.

판정 시 현재 커밋, 필요한 검사 종류, 최신 실행 및 결과를 함께 확인합니다. 검사 중인지, 검사에 실패했는지, 검사 자체의 근거가 없는지를 구분하면 실행 대기 상태를 이해하고 올바르게 다시 검사를 요청할 수 있습니다.
