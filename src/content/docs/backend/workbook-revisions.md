title: "사람과 AI가 같은 시트를 편집하면 누구의 변경을 남겨야 할까?"
description: "사람과 AI가 같은 XLSX 파일을 수정할 때 기준 리비전으로 덮어쓰기를 막는 방법입니다."
---

브라우저에서 엑셀 파일을 열고 AI에게 합계 수식을 넣어 달라고 요청했다고 해보겠습니다. AI가 시트를 읽고 다음 작업을 준비하는 사이, 사람이 브라우저에서 그 합계 칸에 값을 입력합니다. 잠시 뒤 AI가 처음 읽은 값을 기준으로 같은 칸을 수정하겠다고 요청합니다.

이때 서버가 마지막으로 들어온 요청을 그대로 적용하면 사람의 수정이 사라집니다. 요청을 보낸 순서와 서버에 도착한 순서가 같아도 문제는 남습니다. AI가 작업을 시작했을 때 본 문서와 지금 서버에 있는 문서가 달라졌으니까요.

Foloom의 XLSX 편집에서 이 문제를 어떻게 다뤘는지 살펴보겠습니다.

## 요청 안에 기준 리비전을 넣었습니다

편집 요청에는 어느 셀에 어떤 값을 넣을지와 함께 `baseRevision`이 들어갑니다. 편집을 결정할 때 읽었던 문서의 리비전입니다.

예를 들어 사람과 AI가 모두 리비전 12를 읽었다고 해보죠. 사람이 먼저 변경을 저장하면 다음 문서 상태는 리비전 13입니다. 뒤이어 리비전 12를 기준으로 한 AI의 요청이 오면 서버에서 충돌을 반환합니다. AI가 다시 문서를 읽었다면 이번에는 리비전 13의 셀 값과 수식을 보고, 처음의 변경이 여전히 필요한지 판단할 수 있습니다.

중요한 건 이 비교를 **브라우저와 AI가 동일하게 거친다**는 점입니다. Foloom에는 AI의 `apply_operations`와 브라우저에서 시작한 `apply_user_operations`가 있지만, 두 도구 모두 같은 워크북 세션의 `Apply`를 호출합니다. 세션은 잠금을 잡은 뒤 현재 리비전과 요청의 리비전을 비교합니다. 읽기와 쓰기 사이에 끼어든 변경을 클라이언트마다 따로 감지할 필요가 없습니다. [MCP 도구 등록](https://github.com/qtaghdi/foloom/blob/6966fe653a43dd5c1dd720f6fd1cac8dd2596f25/internal/transport/httpapi/mcp.go#L329-L357) · [세션의 리비전 비교](https://github.com/qtaghdi/foloom/blob/6966fe653a43dd5c1dd720f6fd1cac8dd2596f25/internal/formats/xlsx/session.go#L157-L183)

## 리비전은 저장된 상태가 달라질 때 바뀝니다

리비전이 같다고 해서 그 자리에서 원본을 바로 바꾸면 어떻게 될까요? 여러 셀을 수정하다가 오류가 나거나, 수정한 파일을 저장하는 단계에서 실패할 수 있습니다. 그때 서버 메모리는 새 상태인데 파일은 이전 상태라면, 다음 요청에서 어떤 상태가 기준인지 애매해집니다.

그래서 현재 워크북의 바이트를 읽어 변경 후보를 만들고, 후보에 요청을 적용합니다. 후보의 저장 결과를 해시로 비교해 같다면 새 리비전을 발급하지 않습니다. 결과에 차이가 있으면 이력 기록을 준비하고 파일을 교체한 뒤 리비전을 올립니다. 파일 교체 단계가 실패하면 기존 워크북을 기준으로 유지합니다. [후보를 준비하는 부분](https://github.com/qtaghdi/foloom/blob/6966fe653a43dd5c1dd720f6fd1cac8dd2596f25/internal/formats/xlsx/session.go#L181-L205) · [바이트 비교와 저장 순서](https://github.com/qtaghdi/foloom/blob/6966fe653a43dd5c1dd720f6fd1cac8dd2596f25/internal/formats/xlsx/session.go#L281-L312)

같은 값을 다시 넣어 저장 결과까지 같다면 번호를 올리지 않는 것도 이 관점에서 이해할 수 있습니다. 내용이 같은데 리비전만 올라가면, 그 사이에 문서를 읽은 다른 편집자가 필요 없는 충돌을 만나게 됩니다.

## 다른 셀을 수정했는데도 충돌이 날 수 있지 않을까요?

그럴 수 있습니다. 이 규칙은 셀마다 버전을 비교하지 않고 워크북 전체의 리비전을 비교합니다. 사람이 A1을 수정하는 사이 AI가 B2를 수정하려 했다면, 둘의 작업을 합칠 수 있어 보여도 뒤에 온 요청은 다시 읽어야 합니다.

스프레드시트에서는 셀 주소만 다르다고 두 작업이 독립적이라고 단정하기 어렵습니다. 행을 삽입하면 주소가 밀릴 수 있고, B2의 수식이 A1을 참조할 수도 있습니다. 충돌 응답을 받았다고 기존 요청에 새 리비전 번호만 붙여서 다시 보내면, 처음 방지하려던 덮어쓰기가 다시 생깁니다.

이 흐름에서 서버가 해주는 일은 판단에 사용한 문서가 여전히 최신인지 확인하는 데까지입니다. 문서가 바뀌었다면 다시 읽고, 새 상태에서도 같은 변경을 원할지 정해야 합니다. 처음 예시로 돌아가면 AI가 판단해야 할 일은 이제 “합계 수식을 넣을까?”보다 조금 더 구체적입니다. “사람이 방금 적은 값을 그대로 두고, 합계는 다른 칸에 넣는 편이 나을까?”라는 질문이 생깁니다.
