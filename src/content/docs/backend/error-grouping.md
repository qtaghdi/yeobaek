title: "같은 오류가 세 번 들어오면 세 건으로 세어야 할까?"
description: "Jabso에서 재전송은 이벤트 ID로 걸러내고, 관련 오류는 지문으로 묶는 이유입니다."
---

오류 수집기에 다음 이벤트가 도착했다고 해보겠습니다.

| 도착 | 이벤트 ID | 메시지 |
| --- | --- | --- |
| 첫 번째 | `evt-a` | 주문 ID 10482 조회 실패 |
| 두 번째 | `evt-a` | 주문 ID 10482 조회 실패 |
| 세 번째 | `evt-b` | 주문 ID 20817 조회 실패 |

두 번째 요청은 첫 이벤트가 다시 전송된 경우라고 가정하겠습니다. 세 번째는 같은 코드에서 오류가 한 번 더 발생한 경우입니다. 조사할 이슈로는 한 항목에 모아보고 싶지만, 새로 발생한 횟수는 두 번이어야 합니다.

Jabso의 수집 코드를 보면 이 두 질문에 각각 다른 키를 사용하는 이유를 확인할 수 있습니다.

## 이벤트 ID는 한 번의 발생을 가리킵니다

수집기가 받는 요청은 오류 자체가 아닙니다. 이미 일어난 오류를 보고하는 메시지입니다. 전송 도중 응답을 받지 못하면 보낸 쪽은 다시 시도할 수 있고, 수집기에는 같은 이벤트 ID가 두 번 올 수 있습니다.

Jabso는 이벤트를 저장할 때 `(project_id, event_id)` 충돌을 확인합니다. 프로젝트 범위가 필요한 이유는 다른 프로젝트에서 같은 이벤트 ID가 들어와도 서로 영향을 주지 않아야 하기 때문입니다. 새 이벤트가 실제로 저장된 경우에만 이슈의 발생 횟수를 증가시킵니다. 저장과 집계가 하나의 트랜잭션에 있으므로, 같은 이벤트가 동시에 들어오더라도 먼저 조회해서 “없었다”는 결과만 믿고 둘 다 횟수를 늘리는 일을 피할 수 있습니다. [이벤트 저장과 집계 코드](https://github.com/qtaghdi/jabso/blob/c9630a9a7802d9f3c86e1bd46b84e08b0e07ccf9/apps/server/src/adapters/persistence/postgres-ingest-event-store.ts#L38-L145)

이때 한 번 저장된다는 설명은 **같은 이벤트 ID를 가진 재전송**에 해당합니다. 새 ID를 만들어 다시 보내면 수집기가 그 요청을 이전 이벤트와 같은 발생이라고 확정할 근거가 없습니다.

## 지문은 어떤 발생들을 한 화면에 보여줄지 정합니다

이벤트 ID만으로는 `evt-a`와 `evt-b`가 비슷한 문제인지 알 수 없습니다. 메시지 전체를 키로 삼으면 주문 번호가 바뀔 때마다 이슈가 하나씩 생기겠죠. 그래서 메시지의 소문자화와 네 자리 이상인 숫자 토큰이나 UUID, URL 등을 자리표시자로 바꾸는 정규화을 거칩니다. 위 예시에서 주문 번호는 둘 다 같은 자리표시자로 바뀝니다.

Jabso의 기본 지문에는 예외 타입과 정규화한 메시지가 들어갑니다. 스택에서도 앱 외부 프레임으로 표시된 항목을 제외하고, 남은 프레임의 마지막 세 개까지 파일명과 함수명을 사용합니다. SDK가 커스텀 지문을 제공하면 그 값을 사용합니다. [기본 지문과 커스텀 지문 구현](https://github.com/qtaghdi/jabso/blob/c9630a9a7802d9f3c86e1bd46b84e08b0e07ccf9/domains/ingestion/server/fingerprint.ts)

여기서 해시가 오류의 원인까지 알아내는 것은 아닙니다. 어떤 입력이 같은지를 빠르게 비교할 수 있게 해주는 값입니다. 같은 예외 타입이라도 다른 파일이나 함수에서 생긴 오류를 분리할 수 있고, 반대로 구분에 필요한 값까지 메시지 정규화에서 지워 버리면 성격이 다른 오류가 묶일 수 있습니다.

## 무엇을 세고 싶은지부터 정해봅시다

맨 처음 표에서 수집기가 관찰한 요청은 세 번입니다. 같은 ID로 다시 온 요청을 제외하면 오류 발생은 두 번입니다. 두 발생의 지문이 같다면 조사 화면에 올라갈 이슈는 하나입니다.

직접 수집기를 만들 때는 이 셋을 한 카운터에 넣기 쉽습니다. 그런데 운영 중에 “전송이 왜 이렇게 많지?”, “사용자가 실제로 오류를 몇 번 만났지?”, “지금 조사할 문제가 몇 개지?”를 묻는 순간 서로 다른 숫자가 필요해집니다. 데이터 모델을 정할 때 각각에 답할 키를 따로 두면, 이슈가 많이 반복되는 상황에서도 수집 횟수와 발생 횟수를 구분해서 볼 수 있습니다.
