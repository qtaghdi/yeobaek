로그인 폼을 만들고 아이디와 비밀번호를 보내봅니다. 사용자 정보도 잘 받아왔습니다. 이쯤이면 인증은 다 붙였다고 생각하기 쉽죠.

이번엔 로그인한 채로 시간을 좀 보내고, 새 탭을 열고, 원래 탭에서 로그아웃해봅시다. 그 뒤에 요청을 보내면 어떤 일이 일어나야 할까요?

## 로그인은 시작일 뿐이다

사용자가 인증에 성공했다면 이후 요청에서도 서버가 그 사용자를 식별할 수 있어야 합니다. 세션의 발급과 만료에 대한 서버의 정책이 필요하고, 프론트는 그 정책을 화면의 상태로 표현해야 합니다.

세션의 유효기간을 무작정 길게 유지하거나 짧게 유지하는 것만으로 해결되는 문제는 아닙니다. 사용자의 작업 흐름, 서비스의 성격, 서버의 보안 정책을 함께 고려해야 합니다. 인증 정보의 저장과 갱신 역시 단순히 구현하기 편하다는 이유만으로 결정하지 않습니다.

## 세션을 확인하는 중인데 로그아웃 상태라고 표시하면?

페이지를 새로고침했습니다. 사용자 정보 요청이 아직 완료되지 않았는데 프론트가 로그인하지 않은 것으로 판단합니다. 잠깐 로그인 페이지가 보였다가 다시 원래 페이지로 돌아옵니다.

이런 현상은 인증 상태를 true와 false 둘로만 생각하면 발생하기 쉽습니다.

```ts
type SessionState =
  | { status: "checking" }
  | { status: "authenticated"; user: User }
  | { status: "anonymous" }
  | { status: "unavailable" };
```

확인 중인 상태와 로그인하지 않은 상태는 다릅니다. 또한 일시적인 통신 실패가 반드시 세션의 종료를 의미하는 것도 아닙니다. 서버의 판단을 기준으로 화면의 상태를 구분해야 사용자가 불필요하게 로그인과 로그아웃을 반복하지 않습니다.

## 로그인한 사용자라면 모든 기능을 사용할 수 있을까?

Authentication은 사용자가 누구인지 확인하는 일입니다. Authorization은 해당 사용자가 특정 작업을 수행할 수 있는지 판단하는 일입니다.

프론트에서 관리자 메뉴를 숨기는 것은 화면 구성입니다. 실제 권한은 서버에서 판단해야 합니다. 그래야 같은 데이터를 여러 클라이언트에서 다루더라도 서비스의 권한 정책이 일관되게 유지됩니다.

따라서 권한이 부족한 경우와 인증 세션이 종료된 경우도 화면에서 같은 오류로 처리할 이유가 없습니다. 사용자에게 필요한 다음 행동이 다르기 때문입니다.

## 외부 로그인 서비스를 사용하면 Auth는 끝일까?

GitHub나 Google 같은 로그인 서비스를 활용하면 서비스가 직접 비밀번호를 관리해야 하는 범위를 줄일 수 있습니다. 하지만 우리 서비스 안에서 사용자가 어떤 계정을 사용하는지, 탈퇴하면 어떤 데이터가 남는지, 연결을 해제하면 다시 어떻게 로그인할지 등의 정책은 여전히 필요합니다.

로그인 버튼을 눌렀을 때 성공하는 것까지 보고 끝내면, 다음날 같은 화면에 들어왔을 때의 상태는 알 수 없습니다. 시간이 지나거나 세션이 끊겼을 때 사용자가 어디에 있게 될지까지 보니 테스트해야 할 장면이 꽤 많았습니다.
