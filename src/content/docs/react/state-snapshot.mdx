버튼 한 번에 숫자를 3 올려보려고 `setCount`를 세 번 호출했습니다. 결과는 1이었습니다. 세 번 다 실행된 게 맞다면, 호출할 때마다 꺼내 쓴 `count`는 도대체 몇이었을까요?

## 렌더마다 다른 count가 있다

React 컴포넌트가 렌더될 때는 그 시점의 상태와 props를 가지고 JSX를 계산합니다. 클릭 핸들러 역시 같은 렌더에서 받은 `count`를 사용합니다. `setCount`를 호출하면 다음 렌더를 요청하지만, 지금 실행하고 있는 함수 안에서 이미 읽은 `count`가 바뀌는 것은 아닙니다.

첫 번째 예제에서 count가 0이라면 세 표현식 모두 0 + 1을 계산합니다. 두 번째 예제는 React가 업데이트 큐를 처리할 때 앞선 계산의 결과를 다음 updater에게 전달합니다. 그래서 0에서 시작해 1, 2, 3이 됩니다. 상태 변경 요청과 현재 렌더에서 읽는 값을 분리해서 생각해보세요.

## 두 버튼을 눌러봅시다

두 버튼은 각각 증가 연산을 세 번 요청합니다. 어떤 결과가 나오는지 비교해 보세요.

```tsx
setCount(count + 1);
setCount(count + 1);
setCount(count + 1);
```

기존 상태를 바탕으로 연속 갱신해야 할 때는 다음과 같이 updater를 사용합니다.

```tsx
setCount((previous) => previous + 1);
setCount((previous) => previous + 1);
setCount((previous) => previous + 1);
```

그렇다고 모든 setter에 함수를 전달할 필요는 없습니다. 입력받은 문자열로 값을 교체하는 것처럼 이전 상태를 읽을 이유가 없다면 값을 그대로 전달해도 됩니다. 이전 갱신의 결과를 바탕으로 다음 값을 계산해야 할 때 차이가 생깁니다.

[React: State as a Snapshot](https://react.dev/learn/state-as-a-snapshot)

위 두 코드는 각각 한 번의 클릭 핸들러 안에서 세 번의 상태 갱신을 요청합니다. 세 번의 별도 클릭을 비교하는 것이 아닙니다. 클릭이 각각 끝나고 중간에 새로운 렌더링이 발생한다면 직접 갱신하는 방식도 이전 클릭에서 변경된 값을 읽을 수 있습니다. 이 점을 구분해야 함수형 갱신을 언제 사용해야 하는지 정확히 이해할 수 있습니다.

## 나중에 실행되는 콜백은 무엇을 보고 있을까?

복사 버튼이나 Toast에 타이머를 붙이면 이전 알림의 타이머가 다음 알림을 닫을 수 있습니다. [Oddmash UI #95](https://github.com/Oddmash/oddmash-ui/issues/95)처럼 콜백이 발생한 시점과 실제 실행 시점이 다른 상황에서는 자신이 관리하는 알림을 식별하는 ID가 필요합니다. 단순히 setter를 함수형으로 바꾸는 것만으로 모든 문제가 해결되는 것은 아닙니다.
