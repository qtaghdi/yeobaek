API를 붙이고 성공 케이스까지 잘 나오면 기분이 좋습니다. 그런데 실패 케이스를 처리하기 시작하면 갑자기 손이 멈춥니다. 권한이 없다면 어떻게 하지? 서버가 내려가면? 영어로 전달받은 에러 메시지를 그대로 보여줘야 하나?

이런 고민은 API를 연결할 때마다 반복됩니다.

모든 API의 catch에서 이런 고민을 반복하는 구조라면 차라리 에러를 한 번 정리하고 각 화면에 전달하는 방법을 생각해볼 수 있습니다.

## 서버 메시지를 그대로 보여주면 안 될까?

서버가 `Forbidden`을 반환했다고 해봅시다. 개발자에게는 충분한 정보일 수 있습니다. 하지만 일반 사용자에게 필요한 정보는 왜 현재 행동을 할 수 없는지, 다음에는 무엇을 해야 하는지입니다.

메시지가 서버에서 결정되면 서비스의 언어를 변경했을 때 프론트가 원하는 표현으로 바꾸기도 어렵습니다. 서버와 클라이언트가 고정된 오류 코드에 합의하고, 사용자에게 보여줄 문장은 프론트에서 맥락에 맞게 작성하는 편이 좋습니다.

```ts
type AppError = {
  code: string;
  status: number | null;
};

const errorMessages = new Map<string, string>([
  ["VALIDATION_FAILED", "입력한 내용을 다시 확인해주세요."],
  ["NOT_AVAILABLE", "지금은 사용할 수 없는 기능입니다."],
]);

const getErrorMessage = (error: AppError) =>
  errorMessages.get(error.code) ?? "요청을 처리하지 못했습니다. 다시 시도해주세요.";
```

여기서 중요한 건 모든 오류를 문구 하나로 덮자는 뜻이 아닙니다. 서버 응답을 사용자에게 전달하기 전에 의미를 정리하자는 것입니다. 디버깅에 필요한 정보와 실제 화면에 노출할 문구는 서로 다른 목적을 갖습니다.

예시 응답을 바꿔 보면 화면 문구가 서버의 영어 메시지 대신 오류 코드에 따라 결정됩니다. 서버가 새로 추가한 코드를 프론트가 아직 모르는 경우에는 기본 문구를 사용합니다.

## 모달 안에서 요청 하나 실패했는데 에러 페이지로 보내야 할까?

상품 목록을 보고 있는 중에 수정 모달의 저장 요청이 실패했습니다. 이때 전체 화면을 에러 페이지로 보내버리면 사용자는 확인하던 목록도, 작성 중이던 폼도 잃을 수 있습니다.

그렇다고 모든 컴포넌트에서 catch와 toast를 직접 작성하고 싶지는 않습니다.

그래서 저는 에러의 성격을 먼저 나누고 싶었습니다.

| 위치 | 책임 |
| --- | --- |
| HTTP 클라이언트 | 전송 실패와 응답 형식을 공통 오류 형태로 정리 |
| QueryClient | 공통 실패 정책과 기본 피드백 |
| 개별 화면 | 폼 필드 오류, 인라인 재시도처럼 맥락이 필요한 처리 |

전역 오류 처리에서 페이지 이동을 결정하는 것은 신중해야 합니다. 오류를 처리했다는 이유로 실패를 정상 응답으로 바꿔버리면 호출자는 저장이 성공했다고 오해할 수 있습니다. 처리는 하되 실패라는 사실은 호출자에게 전달되어야 합니다.

## Toast가 두 번 뜬다면?

전역 MutationCache에서 오류 알림을 표시하고 개별 mutation의 onError에서도 알림을 표시한다고 해봅시다. 사용자에게는 한 번 실패했는데 두 번의 Toast가 뜹니다.

그래서 특정 오류를 직접 처리해야 하는 화면은 공통 알림을 생략할 수 있도록 정책을 두는 편이 좋습니다. React 바깥에서 알림을 호출해야 한다면 알림 함수와 UI를 연결하는 인터페이스를 제공할 수 있습니다. 다만 컴포넌트가 사라졌는데 이전 알림 함수가 남아있지 않도록 생명주기도 함께 생각해야 합니다.

## 에러를 없애는 구조가 아니라 에러를 다루는 구조

프론트에서 서버의 실패를 모두 막을 수는 없습니다. 다만 실패를 전달받은 뒤 어떻게 보여줄지는 결정할 수 있습니다.

성공한 요청 하나 만드는 것보다 실패해도 사용자가 다음 행동을 할 수 있는 화면을 만드는 일이 더 귀찮은 경우도 많습니다. 그 귀찮음을 모든 화면에 복제하지 않는 것이 에러 처리 구조를 만드는 이유입니다.
