모달을 띄우고 Escape로 닫아봅니다. 여기까진 잘 되네요. 그런데 마우스를 내려놓고 같은 동작을 해보면 확인할 게 하나 더 생깁니다.

모달을 닫은 다음 Tab을 누르면 어디로 갈까요? 닫기 전까지만 확인했다면 놓치기 쉬운 문제입니다.

개발자에게는 `isOpen`이 바뀌는 일일 뿐이지만 사용자에게는 하나의 조작 과정입니다.

## 모달이 열린 동안 바뀌는 것

1. 트리거를 통해 열린다.
2. 모달 안의 적절한 요소에 포커스를 둔다.
3. 모달이 열린 동안 배경을 조작하지 않도록 한다.
4. 닫힌 뒤 가능한 한 기존 트리거에 포커스를 돌려준다.

실제 포커스 대상은 콘텐츠에 따라 다릅니다. 위험한 삭제를 확인하는 대화상자에서는 가장 안전한 행동이 적절할 수 있습니다. 긴 설명이라면 처음부터 읽을 수 있도록 제목이나 내용을 대상으로 잡는 것도 방법입니다.

예를 들어 상품 삭제 버튼을 누르고 확인 창을 열었다가 취소했다면 다시 그 상품의 삭제 버튼으로 돌아가는 것이 자연스럽습니다. 하지만 실제로 상품을 삭제했다면 버튼 자체가 없어질 수 있습니다. 그때는 주변 목록이나 제목처럼 계속 탐색할 수 있는 위치를 선택해야 합니다.

## 브라우저의 dialog를 써보면

```tsx
const dialog = useRef<HTMLDialogElement>(null);
const closeButton = useRef<HTMLButtonElement>(null);

const openDialog = () => {
  dialog.current?.showModal();
  closeButton.current?.focus();
};

<button onClick={openDialog}>열기</button>
<dialog ref={dialog} aria-labelledby="dialog-title">
  <h2 id="dialog-title">확인</h2>
  <p>내용을 확인하세요.</p>
  <form method="dialog">
    <button ref={closeButton}>닫기</button>
  </form>
</dialog>
```

`showModal()`로 연 네이티브 dialog는 모달의 배경 비활성화 등 기본 동작을 제공하지만, 알맞은 접근 가능한 이름과 초기 포커스는 여전히 설계해야 합니다.

모달의 DOM이 문서 뒤쪽에 있다고 해서 처음 Tab을 눌렀을 때 자동으로 그 영역의 적절한 입력을 찾는다고 가정하면 안 됩니다. 열리는 시점에 대화상자의 이름과 초기 포커스를 명확히 표현하고, 닫힌 뒤 버튼이 실제로 남아 있는지 확인해야 합니다. 이 과정까지 담은 컴포넌트라면 소비자가 모달마다 같은 포커스 처리 코드를 작성할 필요가 줄어듭니다.

## 모달만의 문제는 아닙니다

여러 Toast 중 하나를 제거할 때도 비슷한 일이 생깁니다. 다른 알림이 남아 있는데 포커스를 원래 버튼으로 무조건 돌려버리면 계속 알림을 조작하던 흐름이 끊깁니다. [Oddmash UI #64](https://github.com/Oddmash/oddmash-ui/issues/64)처럼 닫힌 항목에 포커스가 있었을 때만 가까운 조작 가능한 요소로 옮기는 정책을 생각할 수 있습니다.

## 모달을 닫은 뒤 원래 버튼이 없다면?

목록의 삭제 버튼으로 모달을 열었다고 가정해봅시다. 삭제가 성공하면 해당 행과 버튼 자체가 사라집니다.

| 닫힌 이유 | 다음 포커스 후보 |
| --- | --- |
| 취소 | 열었던 삭제 버튼 |
| 삭제 성공 | 다음 행의 조작 버튼 또는 목록 제목 |
| 페이지 이동 | 새 문서의 적절한 시작 지점 |

이런 경우에는 항상 이전 DOM 노드에 focus를 호출하는 것만으로 충분하지 않습니다. 이전 위치가 계속 존재하는지 확인하고, 사용자가 작업 결과를 이해한 다음 자연스럽게 다음 작업을 할 수 있는 지점을 선택해야 합니다.
