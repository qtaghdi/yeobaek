## 한글은 다 표시됐는데 왜 읽기 불편할까?

제목이 한 줄에 안 들어가는 건 괜찮습니다. 그런데 줄 끝에 단어가 어색하게 끊기거나 마지막 줄에 몇 글자만 남으면 같은 제목도 읽기 어렵습니다.

[Juliya](https://github.com/Oddmash/juliya)에서 한국어 줄바꿈을 다루면서도 이 차이를 먼저 봐야 했습니다. 글자가 들어가는지 확인하는 것만으로는 부족했거든요.

예를 들어 좁은 카드에서 `패키지 매니저`라는 표현이 서로 다른 줄에 배치되면 화면에는 모두 표시되지만 읽는 흐름이 끊깁니다. 반대로 단어를 무조건 함께 유지하면 긴 기술 용어가 화면 밖으로 넘어갈 수 있습니다. 줄바꿈은 이 두 요구를 함께 다루어야 합니다.

아래 애니메이션은 줄바꿈 경계의 차이를 설명하는 장면입니다. 실제 Juliya 엔진을 실행한 비교 결과는 아닙니다.

## CSS로 할 수 있는 범위

```css
.heading {
  word-break: keep-all;
  overflow-wrap: anywhere;
  text-wrap: balance;
}
```

- `word-break: keep-all`: 한국어처럼 CJK 문자 사이에서 발생할 수 있는 줄바꿈을 제한합니다.
- `overflow-wrap: anywhere`: 다른 적절한 줄바꿈 기회가 없을 때 긴 문자열을 나눌 수 있게 합니다. 최소 콘텐츠 크기 계산에도 영향을 줄 수 있습니다.
- `text-wrap: balance`: 여러 줄에 텍스트가 배치될 때 줄 길이를 균형 있게 만드는 데 도움을 줍니다.

`keep-all`을 써도 `패키지 매니저`의 공백에서는 줄이 바뀔 수 있습니다. 카드 폭을 조금씩 줄이면 세 카드에서 같은 문장이 어디에서 나뉠까요? 비교할 문장에 공백이 없는 긴 기술 용어나 여러 어절을 직접 입력해도 세 카드에 같은 내용이 즉시 반영됩니다. 세 카드 모두 긴 단어가 화면 밖으로 나가지 않도록 `overflow-wrap: anywhere`를 적용했습니다.

CSS가 제공하는 것만으로 충분한 문장에는 스크립트를 도입할 필요가 없습니다. 특정 단어 조합이나 언어별 문장 경계를 비용으로 평가해야 할 때에만 추가적인 로직이 필요합니다.

## 글자 수 대신 실제 폭

같은 8글자라도 `WWWWWWWW`와 `iiiiiiii`의 폭은 가변 폭 글꼴에서 다를 수 있습니다. 글꼴 크기, 굵기, 글자 간격, 언어별 fallback까지 바뀌면 단순 문자 수 기반 계산은 실제 화면과 다른 결과를 만듭니다.

그렇다면 실제 폭은 어떻게 측정할 수 있을까요? 화면에서 요소의 너비를 읽는 방법과 문자열 자체의 너비를 계산하는 방법은 서로 다릅니다.

| 측정 | 의미 |
| --- | --- |
| clientWidth | padding을 포함하는 정수 CSS 픽셀 너비, border와 세로 스크롤바 제외 |
| getBoundingClientRect().width | border box의 화면상 너비, 변환이 포함될 수 있고 소수점 값 가능 |
| ResizeObserver contentRect.width | 관찰 대상의 콘텐츠 박스 너비 |
| Canvas measureText().width | 지정한 글꼴 설정에서 문자열을 그릴 때의 advance width |

Juliya [#1](https://github.com/Oddmash/juliya/issues/1)에서는 정수로 반올림된 clientWidth에서 추가로 1px을 빼던 방식 때문에 CSS에서는 들어가는 문장이 한 줄 더 밀리는 문제가 기록되었습니다. 현재 DOM 관찰 코드는 content-box 측정값을 우선 사용합니다. 초기 관찰 전에는 계산된 폭이 정수 fallback과 충분히 가까운지 확인해 소수점 값을 선택합니다.

### 같은 폭을 비교하지 않으면 측정도 틀린다

[#3](https://github.com/Oddmash/juliya/issues/3)에는 macOS의 한국어 serif fixture에서 DOM 781.33px, 언어 속성을 설정하지 않은 Canvas 746.83px이 측정된 사례가 있습니다. 두 값은 해당 환경의 기록이며 다른 글꼴에서 같은 차이가 난다는 뜻은 아닙니다.

문자열과 font-family를 같게 지정해도 브라우저가 언어에 따라 다른 fallback 글꼴을 선택하면 결과가 달라질 수 있습니다. 실제 구현은 요소에서 상속된 language를 찾아 Canvas에 전달하고 font, letterSpacing, wordSpacing, fontKerning을 함께 맞춥니다.

```ts
const style = getComputedStyle(element);
const canvas = document.createElement("canvas");
canvas.lang = element.closest("[lang]")?.getAttribute("lang") ?? "";
const context = canvas.getContext("2d");

if (context) {
  context.font = style.font;
  const width = context.measureText("패키지 매니저").width;
  console.log(width);
}
```

이는 측정 원리를 설명하기 위해 축약한 예제입니다. 실제 라이브러리는 spacing 지원 여부와 유효하지 않은 측정값, 관찰 시점도 처리합니다.

## 줄바꿈 결과를 어떻게 선택할까?

이제 사용할 수 있는 폭과 실제 문자열의 너비를 알았으니 어디를 나눌지 결정해야 합니다. Juliya에서는 이 일을 DOM과 분리했습니다. core는 문자열, 가용 폭, 측정 함수를 입력으로 받고, DOM이나 프레임워크 adapter는 실제 화면의 측정값을 제공한 뒤 선택된 경계를 렌더링합니다.

| 단계 | 책임 |
| --- | --- |
| Segmentation | 명시적인 개행과 문단, 텍스트 경계 구분 |
| Boundary candidates | 다음 줄로 나눌 수 있는 위치와 폭 계산 |
| Layout | 후보 중 사용할 경로 선택 |
| Rendering | 결과를 원래 문자열의 범위와 개행으로 변환 |

현재 공개 소스에서 greedy 방식은 각 줄에 가능한 마지막 후보를 선택합니다. balanced 방식은 뒤쪽 경계부터 가능한 줄 선택을 비교합니다. 줄 수가 적은 결과를 우선하고, 줄 수가 같으면 가용 공간 및 경계에 대한 누적 비용을 비교합니다.

이를 쉬운 숫자로 설명하면 폭 12인 영역에 단어들이 5, 2, 3, 4의 너비를 가지고 단어 사이의 공백이 1이라고 가정해 봅시다. 첫 줄에 최대한 많이 넣으면 각 줄의 너비는 12와 4가 됩니다. 두 줄의 길이를 고르게 맞추려면 두 단어씩 배치해 8과 8로 만들 수도 있습니다. 여기에 수식어 뒤, 문장의 종료, 기술 용어 조합처럼 나누기 좋은지에 대한 추가 비용이 들어가면 균형이 비슷한 후보에서도 선택이 달라집니다.

[#123](https://github.com/Oddmash/juliya/issues/123)은 `패키지 매니저`와 같은 기술 명사구가 균형 줄바꿈 중 나뉘는 문제입니다. 규칙은 일부 표현의 분리 비용을 높입니다. [Juliya 0.4.4](https://github.com/Oddmash/juliya/releases/tag/v0.4.4)에서는 `어색하게 끊기거나`처럼 부사어와 서술어가 이어지는 표현도 같은 줄 수와 폭 안에서 되도록 유지합니다. 이를 일반적인 자연어 분석이나 절대적인 분리 금지로 설명해서는 안 됩니다. *공간이 부족하거나 다른 후보가 없으면 나누어야 할 수도 있습니다.*

여기서 한 가지 주의할 점은 **균형이 좋은 줄바꿈과 읽기 좋은 줄바꿈이 항상 같지는 않다는 것입니다.** 두 줄의 길이가 거의 같은 결과라도 기술 용어가 가운데서 잘리면 읽는 사람이 의미를 파악하기 어려워질 수 있습니다. 반대로 모든 표현을 하나의 묶음으로 강제하면 좁은 카드에 배치할 수 없게 됩니다. 그래서 경계에 대한 비용은 절대적인 금지 규칙이 아니라 여러 조건을 비교하는 기준으로 활용합니다.

## 인라인 마크업을 유지하는 이유

`<strong>`과 링크를 포함한 문단은 단순한 문자열과 다릅니다. 텍스트 전체를 새 노드로 바꾸면 강조, 링크의 클릭 동작, 요소에 연결된 상태까지 사라질 수 있습니다.

Juliya의 인라인 구현은 텍스트 노드를 순회해 원래 문자열에서의 시작·끝 위치를 기록합니다. 각 구간의 글꼴과 언어에 맞는 측정 함수를 사용하고, 선택된 위치에 자신이 생성한 개행 요소를 표시합니다. 다시 계산하거나 해제할 때 원래 마크업을 복원할 수 있도록 자체 변경을 따로 관리합니다.

```html
<p lang="ko">
  실제 <strong>글꼴 측정</strong>이 줄바꿈의 기준입니다.
</p>
```

위처럼 이미 의미가 있는 요소를 제거하지 않는 것이 목표입니다. 사용자 입력, 링크의 상호작용 등 민감한 영역에는 adapter의 실제 지원 범위를 확인한 뒤 적용해야 합니다.

## 줄바꿈은 어디까지 브라우저에 맡길까?

한 줄에 정확하게 맞는 폭에서도 강제로 줄이 나뉜다면 알고리즘이 과하게 개입한 것입니다. 반대로 아주 좁은 폭에서 긴 단어 하나가 바깥으로 나간다면 의미 단위를 유지한다는 원칙만 고집할 수는 없습니다. 글꼴이 바뀌거나 제목 안에 강조 태그가 있을 때도 원문의 의미와 순서는 그대로 남아야 합니다.

여백에서도 제목, 한국어 문단, 단순한 강조 마크업에 Juliya를 적용합니다. 링크나 코드가 섞인 내용은 CSS로 균형 있게 배치하고, Juliya가 계산한 줄이 실제 본문 폭을 넘는 경우에도 CSS로 돌아가도록 합니다. 특히 화면에 표시된 뒤에 개행 위치가 바뀌면 오히려 읽는 흐름을 방해할 수 있습니다. 실제로 여백에서 이 현상이 발견되어 [Juliya #155](https://github.com/Oddmash/juliya/issues/155)에 최초 렌더링과 재계산 시점을 구분해 기록했습니다. 자체 라이브러리를 만들었다고 모든 글에 적용할 이유는 없으니까요.

화면 크기가 달라져도 본문 폭은 그대로일 수 있습니다. 그때 미디어 쿼리가 강조 글자의 크기만 바꾸면 이전에 계산한 줄바꿈이 맞지 않을 수 있습니다. 개행을 위해 넣은 `<br>`이 `:first-child` 같은 선택자의 결과까지 바꾸면, 개행이 들어간 DOM의 스타일만 보고는 변경을 놓칩니다. [Juliya 0.4.3](https://github.com/Oddmash/juliya/releases/tag/v0.4.3)에서는 뷰포트가 바뀌면 기존 폭이 같아도 생성한 개행을 걷어낸 상태에서 스타일을 다시 확인합니다.


## 줄 나누기의 비용을 비교할 때

설명용으로 같은 폭의 컨테이너에서 문자열이 두 줄로 나뉘는 경우를 생각해봅시다. 첫 줄이 길고 둘째 줄에 한 단어만 남는 후보와 두 줄의 길이가 비슷한 후보는 서로 다른 읽기 경험을 만듭니다. 단순히 빈 공간의 합을 비교하면 어느 단어가 의미상 함께 있어야 하는지는 알 수 없습니다.

실습에서 같은 문장을 좁은 폭과 넓은 폭에 넣어 보세요. 줄 수가 같은 경우에도 나뉘는 경계가 달라지는 이유를 비교해보면, 글꼴 측정과 의미 경계가 각각 독립된 입력인 이유를 이해할 수 있습니다.
