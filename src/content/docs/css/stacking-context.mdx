헤더 뒤로 모달이 숨어서 `z-index: 9999`를 줬습니다. 안 나옵니다.

> 그럼 9를 하나 더 붙이면 되나?

여전히 헤더 뒤에 있습니다. 애초에 헤더와 모달의 숫자를 서로 비교하긴 하는 걸까요?

## 직접 숫자를 바꿔봅시다

부모 A의 값을 1로 바꾸고 자식 A의 값을 9999로 유지해 보세요. 부모 B는 2입니다. 이어 부모 A를 3으로 바꾸면 어떻게 될까요?

장면 아래의 비교 범위를 보면 자식이 별도 맥락 안에 들어가는지 확인할 수 있습니다. 부모 A의 z-index를 auto로 되돌린 뒤 transform이나 isolation을 켜면 명시적인 숫자가 없어도 부모 A가 새로운 맥락을 만들고 자식의 숫자는 그 안으로 들어갑니다.

부모 A가 1이고 부모 B가 2라면 자식 A의 9999는 A 안에서의 순서일 뿐입니다. 쉽게 말하면 다른 아파트에 사는 사람끼리 층수만 비교해서 누가 더 높은 곳에 있는지 결정하는 셈입니다. 먼저 건물 자체가 어떻게 놓여 있는지 봐야 합니다.

## 자식은 부모의 순위를 벗어날 수 없다

앞의 예제에서 부모 A가 하나의 쌓임 맥락을 형성하면 자식의 9999는 그 안에서만 의미가 있습니다. 부모 A와 B를 비교하는 단계에서는 A 내부의 숫자가 아니라 부모 자체의 쌓임 순서를 봅니다.

위치 지정 요소의 정수 `z-index` 외에도 `transform`, 1보다 작은 `opacity`, `isolation: isolate`처럼 쌓임 맥락을 만드는 조건이 있습니다. 따라서 문제가 발생했을 때 자식의 숫자만 확인해서는 원인을 찾기 어렵습니다.

부모 A와 B가 동일한 양의 스택 레벨이라면 소스 순서 등 페인팅 순서도 고려해야 합니다. 따라서 아래 비교 범위는 어느 요소의 숫자를 비교해야 하는지 설명하는 것이지, 모든 CSS 페인팅 규칙의 결과를 계산하는 것은 아닙니다. 실제 겹침은 위 장면의 브라우저 렌더링으로 확인합니다.

## 숫자를 올리기 전에 부모부터

```css
.overlay-root {
  position: relative;
  z-index: 3;
}
```

모달이 다른 영역에 가려져 있다면 먼저 조상 요소 중 누가 별도의 쌓임 맥락을 만들고 있는지 찾아봅시다. 모달을 공통 오버레이 영역에 배치하는 방법도 있습니다. 숫자를 올리는 것보다 비교되는 범위를 바꾸는 것이 중요한 상황이죠.

Portal로 모달을 옮겨도 일은 끝나지 않습니다. 브라우저에서 실제로 어느 부모 아래에 들어갔는지 보고, 그 부모의 쌓임 맥락을 확인해야 합니다. 화면에서 위에 보인다면 이번에는 Tab을 눌러보세요. 쌓이는 순서를 고쳤다고 포커스가 따라오지는 않습니다.

## Toast와 모달이 동시에 나왔다면?

[Oddmash UI #46](https://github.com/Oddmash/oddmash-ui/issues/46)의 경우에는 어느 레이어를 보여줄지만큼 어느 레이어를 조작할 수 있게 할지도 중요했습니다. Toast가 모달 위에 보인다고 해서 배경까지 조작할 수 있어야 하는 건 아니죠. 포털과 부모 쌓임 맥락을 먼저 확인하고 역할에 맞는 레이어 정책을 정하는 편이 숫자 경쟁보다 낫습니다.
