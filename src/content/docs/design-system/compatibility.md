공용 UI 라이브러리의 props 이름이 마음에 들지 않아 변경했습니다. 라이브러리 자체는 빌드가 잘 됩니다. 그런데 이걸 사용하는 다른 앱에서는 기존 이름으로 호출하고 있습니다. 라이브러리를 만드는 입장과 사용하는 입장의 차이가 드러나는 순간입니다.

## 공개 API에 포함되는 것은 생각보다 많다

| 변경 | 확인할 영향 |
| --- | --- |
| Props 이름 | 호출하는 프로젝트의 컴파일 및 동작 |
| CSS 클래스·토큰 | 스타일을 덮어쓰는 사용처 |
| 이벤트·키보드 동작 | 기존 사용자 조작 및 접근성 |
| 패키지 내보내기 | 빌드, SSR 및 하위 경로 import |

예를 들어 `onChange` 콜백이 선택한 값을 넘겨주던 API를 DOM 이벤트로 변경한다면 타입뿐 아니라 콜백을 사용하던 코드의 동작까지 바뀝니다. 내부 구현만 바꾸는 것과 소비자에게 수정을 요구하는 것은 전혀 다른 일이죠.

그래서 기존 이름을 바로 제거할지, 호환 별칭을 두고 점진적으로 변경할지부터 생각해봅니다. 공개 API를 제거한다면 변경 내용과 실제 마이그레이션 예제를 남겨야 합니다. 버전 번호만 보고 호환된다고 판단하기보다는 실제 소비 앱에서 확인하는 편이 좋습니다.

## 다른 환경에서도 같은 계약을 제공하는가

[Boundra #140](https://github.com/Oddmash/boundra/issues/140)의 프레임워크별 호환성 논의처럼 공개 진입점과 결과의 의미는 소비자 환경이 달라도 유지되어야 합니다. 실제 소비 앱에서 빌드해보는 것이 내부 테스트만 통과시키는 것보다 많은 정보를 줍니다.
