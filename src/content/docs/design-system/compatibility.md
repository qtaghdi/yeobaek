공용 컴포넌트의 props 이름이 마음에 걸려서 바꿨습니다. 라이브러리는 잘 빌드됩니다.

근데 버전을 올린 앱은 여전히 이전 이름으로 컴포넌트를 호출합니다. 라이브러리에서 한 줄 바뀐 일이 앱에서는 어떤 문제가 되는지부터 봅시다.

## 공개 API에 포함되는 것은 생각보다 많다

| 변경 | 확인할 영향 |
| --- | --- |
| Props 이름 | 호출하는 프로젝트의 컴파일 및 동작 |
| CSS 클래스·토큰 | 스타일을 덮어쓰는 사용처 |
| 이벤트·키보드 동작 | 기존 사용자 조작 및 접근성 |
| 패키지 내보내기 | 빌드, SSR 및 하위 경로 import |

예를 들어 `onChange` 콜백이 선택한 값을 넘겨주던 API를 DOM 이벤트로 변경한다면 타입뿐 아니라 콜백을 사용하던 코드의 동작까지 바뀝니다. 내부 구현만 바꾸는 것과 소비자에게 수정을 요구하는 것은 전혀 다른 일이죠.

이럴 때 저는 먼저 실제 앱 하나를 열어 버전을 올려보는 게 좋다고 생각합니다. 라이브러리 빌드가 녹색이어도 그 앱이 여전히 이전 콜백을 쓰고 있을 수 있습니다. 별칭을 남길지 제거할지 정했다면, 앱에서 실제로 어떤 코드를 바꿔야 하는지도 예제로 남겨두면 좋습니다.

## 다른 환경에서도 같은 계약을 제공하는가

[Boundra #140](https://github.com/Oddmash/boundra/issues/140)의 프레임워크별 호환성 논의처럼 공개 진입점과 결과의 의미는 소비자 환경이 달라도 유지되어야 합니다. 실제 소비 앱에서 빌드해보는 것이 내부 테스트만 통과시키는 것보다 많은 정보를 줍니다.

## 소비자가 변경을 알아차리는 시점

예를 들어 이전 버전의 선택 컴포넌트 콜백은 value를 받고 새 버전의 콜백은 event를 받는 가상의 변경을 생각해봅시다. 내부 함수 이름만 바꿀 때와 달리 소비자의 기존 호출 코드는 새 계약에 맞춰 수정해야 합니다.

| 점검 | 확인 방법 |
| --- | --- |
| 타입 호환성 | 기존 소비자 예제의 컴파일 |
| 동작 호환성 | 동일한 키보드 선택과 폼 제출 결과 |
| 배포 호환성 | 실제 패키지에서 기존 import 진입점 확인 |
| 변경 전달 | 릴리스 문서에 변경 범위와 전환 예제 제공 |

실제 소비자의 기존 계약을 확인하면 사용자가 직접 수정해야 하는 변경과 내부 개선을 구분하는 데 도움이 됩니다.
