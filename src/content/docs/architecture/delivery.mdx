## 빌드에 성공했는데 왜 배포된 웹은 404일까?

로컬에서 열어본 페이지를 배포했습니다. CI에서도 빌드가 통과했는데, 배포 주소로 들어가니 404가 뜹니다.

분명 빌드는 됐습니다. 그럼 빌드가 만든 파일은 어디에 있고, 지금 이 주소는 무슨 파일을 찾고 있을까요?

빌드가 성공했다는 것은 배포할 결과물이 만들어졌다는 뜻입니다. 그 결과물이 실제 사용자에게 올바른 경로로 전달되는지는 별도로 확인해야 합니다.

## 검증의 단계

| 단계 | 확인해야 할 결과 |
| --- | --- |
| 고정 의존성 설치 | 선언한 버전과 lockfile이 일치 |
| 타입·린트·테스트 | 실제 검증하려는 계약과 코드가 일치 |
| 프로덕션 빌드 | 배포할 파일 및 진입점 생성 |
| 배포 | 검증한 결과물이 대상 환경에 게시 |
| 배포 후 확인 | 실제 주소에서 페이지와 자산, 인터랙션 동작 |

로컬에서 빌드에 성공하면 위 단계 중 일부를 확인한 것입니다. 그렇다면 실제 배포 주소가 404를 반환했을 때 빌드부터 다시 의심하기보다 어느 단계에서 결과가 달라졌는지를 확인하는 편이 좋습니다. 특히 정적 사이트에서는 HTML을 만드는 방식과 그 파일을 공개하는 방식이 다릅니다.

## 렌더링과 실행 환경

정적 생성은 빌드 시점에 문서를 준비합니다. 서버 렌더링은 요청 시점에 서버가 HTML을 생성할 수 있고, 클라이언트에서 조작이 필요한 영역은 브라우저에서 실행합니다. 인터랙티브한 기술 문서라고 페이지 전체를 클라이언트에서 다시 구성해야 하는 것은 아닙니다.

여백에서는 Astro Starlight로 본문을 정적으로 생성하고, 필요한 React 예제만 문서에서 하이드레이션합니다. 전체 페이지를 React 앱으로 만들지 않아도 읽을 수 있는 HTML과 조작 가능한 예제를 함께 제공할 수 있습니다. JavaScript가 로드되지 않은 경우에도 본문과 링크가 읽혀야 합니다.

## 빌드 결과를 실제 URL에서 확인하기

Oddmash Website의 [#23](https://github.com/Oddmash/oddmash-website/issues/23)과 [PR #24](https://github.com/Oddmash/oddmash-website/pull/24)은 GitHub Pages 프로젝트 경로의 실제 배포를 다뤘습니다. 프로젝트 Pages는 도메인의 루트가 아니라 저장소 이름 아래에서 제공할 수 있습니다. 여백 역시 `/yeobaek/`로 배포됩니다.

```js
export default defineConfig({
  site: "https://qtaghdi.github.io",
  base: "/yeobaek",
});
```

예를 들어 앱의 CSS가 `/_astro/main.css`로 렌더링되었다면 이 주소는 도메인의 루트를 가리킵니다. 실제 파일이 `/yeobaek/_astro/main.css`에 게시됐다면 빌드가 성공했더라도 사용자에게 스타일이 전달되지 않을 수 있습니다.

아래 예제의 이미지 파일은 여백에 실제로 배포된 파비콘입니다. 도메인 루트로 바꿔 보면 문서는 그대로 읽을 수 있지만 같은 파일 이름으로 아이콘을 가져오지는 못합니다.

## 검증 결과를 다른 리비전에 재사용할 때

[Oddmash Website #60](https://github.com/Oddmash/oddmash-website/issues/60)에서는 PR에서 이미 실행한 Chromium, Firefox, WebKit 전체 테스트를 동일한 내용이 main에 병합된 뒤 다시 실행하는 비용을 검토했습니다.

PR에서 통과했다는 사실만 확인하면서 main 검사를 생략하면 병합 직전에 다른 변경이 들어온 경우 잘못된 근거를 재사용할 수 있습니다. 고려할 조건은 검증한 대상의 동일성과 근거의 최신성입니다.

| 상황 | 판단 |
| --- | --- |
| 검증한 PR과 main의 tree가 정확히 일치하고 최신 필수 검증 성공 | 해당 근거 재사용을 검토 |
| 다른 변경이 병합되어 tree가 다름 | 전체 검증 실행 |
| 검증 근거를 조회하지 못함 | 전체 검증 실행 |
| 검증이 실패·취소·미완료됨 | 전체 검증 실행 |

이 접근은 테스트의 의미를 줄이는 것이 아니라 동일한 결과물을 다시 검사하는 일을 줄일 수 있는 조건을 정하는 것입니다. 별도의 Pages 빌드와 실제 게시 확인까지 생략하는 의미가 아닙니다.

정확한 비용 절감 수치는 동일한 CI 환경에서 실행 시간과 반복 여부를 측정한 경우에만 기록할 수 있습니다. 기획이나 구현 이슈만으로 절감량을 추정해서는 안 됩니다.

## 배포 환경과 모듈 경계

Oddmash Agents의 [#292](https://github.com/Oddmash/oddmash-agents/issues/292)에서는 새로운 배포 아티팩트가 환경의 함수 개수 제한에 걸린 상황을 다뤘습니다. 화면의 기능이 정상 동작하고 컴파일되더라도 플랫폼이 배포할 수 있는 형태인지 확인해야 합니다.

이런 상황에서는 공개 URL과 허용되는 요청의 계약을 보존하면서 내부 배포 단위를 통합할 수 있습니다. 단순히 경로를 삭제하거나 중요한 요청 검증을 없애는 방식으로 제한에 맞추어서는 안 됩니다. 변경 전후의 아티팩트 구성과 실제 대상 경로의 동작을 확인해야 합니다.

## 배포가 끝났다고 판단하는 시점

GitHub Actions에 초록색 체크가 뜬 것과 실제 사용자가 페이지를 볼 수 있는 것은 별개입니다. 정적 사이트라면 하위 경로의 주소를 직접 열어도 HTML과 자산이 정상적으로 로드되는지 확인해야 합니다. 검색과 인라인 예제가 있다면 클릭해서 실제로 동작하는지도 봐야겠죠.

배포가 어긋났다면 먼저 공개 주소가 어떤 리비전을 내보내는지 확인합니다. 어제 배포가 성공했다는 기록은 오늘 빌드한 파일이 올라갔다는 답이 되지 않습니다. 주소에서 파일로, 파일에서 빌드로 거슬러 보면 어디에서 끊겼는지 좁히기 쉽습니다.


## 어떤 결과물을 배포했는지 기록합니다

같은 프로젝트에서 빌드 A는 통과했고 빌드 B는 이후 수정된 파일로 새로 생성되었다고 가정해봅시다. 실제 공개 사이트에 A와 B 중 무엇이 올라갔는지 기록하지 않는다면 CI 성공 표시 하나로 현재 서비스 상태를 판단할 수 없습니다.

커밋과 빌드 결과물, 배포 대상의 관계를 확인하고 실제 공개 주소에서 CSS·JS 자산과 대표 사용자 행동까지 검사합니다. 배포 단계의 성공과 사용자 화면의 성공을 따로 기록하는 이유입니다.
