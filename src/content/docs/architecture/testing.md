## 테스트가 많으면 정말 버그가 줄어들까?

테스트가 많다고 실제 사용자가 만나는 문제가 모두 줄어드는 것은 아닙니다. 내부 함수가 호출되는 것을 확인하는 테스트가 있더라도 사용자가 버튼을 눌렀을 때 원하는 동작까지 보장한다는 뜻은 아니니까요.

그렇다면 어떤 결과를 확인해야 테스트를 작성한 의미가 있을까요? 컴포넌트 동작부터 Boundra의 캐싱 실험까지 살펴보겠습니다.

## 선택 기준

| 수준 | 확인할 문제 |
| --- | --- |
| 단위 테스트 | 입력의 변환, 규칙, 계산 결과와 경계값 |
| 컴포넌트 테스트 | 사용자 조작에 따른 의미 있는 상태 변화 |
| 통합 테스트 | 실제 모듈, 설정, 어댑터와 공개 계약 |
| 브라우저 테스트 | 실제 키보드, 포커스, 레이아웃, 탐색 |
| 시각 회귀 | 의도한 배치와 상태 표현의 차이 |
| 성능 측정 | 같은 환경과 입력에서 시간·메모리 변화 |

Select라면 내부 state가 무엇인지보다 실제 Enter가 선택을 변경하는지, Escape가 취소인지, 닫힌 뒤 무엇이 포커스되는지를 확인하는 테스트가 소비자 계약과 더 가깝습니다.

라이브러리는 패키지의 실제 설치, import, 타입과 빌드도 확인해야 합니다. 프로젝트 내부에서는 컴파일되지만 외부 소비자의 별칭이나 패키지 exports가 다른 경우 정상 동작하지 않을 수 있습니다.

## 먼저 참조 결과를 만들고 최적화한다

Boundra의 [#142](https://github.com/Oddmash/boundra/issues/142)는 증분 스캔으로 반복 검사 시간을 줄일 수 있는지 검증하는 작업입니다. 전체 스캔은 이미 비교할 기준으로 존재합니다.

같은 workspace에 대해 전체 스캔과 캐시 후보가 서로 다른 진단을 반환한다면 빠른 결과를 사용하는 것만으로는 안전하지 않습니다. 발견한 진단 개수가 같다는 조건도 부족합니다. 한 규칙의 진단이 사라지고 다른 규칙의 진단이 추가되면 총 개수는 동일할 수 있기 때문입니다.

그래서 실제 실험에서는 같은 프로젝트 모델과 설정을 사용해 전체 수집 결과와 캐시 후보를 각각 만들었습니다. 단순히 진단 개수를 비교하는 대신 수집된 결과와 경계 평가 결과가 모두 같은지 확인하도록 구성했습니다.

```ts
const reference = fullScan(workspace);
const candidate = incrementalScan(workspace);

expect(candidate.imports).toEqual(reference.imports);
expect(candidate.diagnostics).toEqual(reference.diagnostics);
```

이 코드는 원리를 보여 주는 TypeScript 의사 코드입니다. 실제 Boundra의 실험은 Rust 테스트로 구성되어 있습니다. 실제 코드는 진단뿐 아니라 전체 수집 결과 자체도 비교하므로 검사 범위가 줄어드는 문제를 발견할 수 있습니다.

### 무엇을 변경했는지가 중요하다

소스 코드만 변경된 상황에서 캐시가 올바르다고 가정하면 안 됩니다. 모듈 해석에 영향을 주는 설정도 검사 결과를 바꿀 수 있습니다.

| 변경 | 기대하는 결과 |
| --- | --- |
| 파일 내용 수정 | 현재 코드의 import와 진단 반영 |
| 새 파일 추가 | 새로운 검사 대상 포함 |
| 파일 삭제 | 삭제된 import와 진단 제거 |
| 별칭 변경 | 동일 import의 해석 결과 변경 반영 |
| 매니페스트 변경 | 패키지와 공개 경계 재평가 |
| 검사 설정 변경 | 전체 검사와 동일한 분석 대상 및 규칙 |
| 동일한 입력 | 진단 및 검사 범위 변화 없음 |

캐시 무효화의 범위는 실제 데이터 의존성을 기준으로 정해야 합니다. 파일 내용이 그대로여도 별칭이 변경되면 동일 문자열이 다른 대상 모듈을 의미할 수 있습니다.

## 정확성 통과와 성능 개선은 다른 결과

2026년 11월 25일 공개 성능 문서에는 두 도메인에 1,000개 파일을 구성한 합성 workspace에서 증분 실험을 수행한 기록이 있습니다. 실험은 전체 결과와 검사 범위의 일치 여부를 검증하지만, 일관된 성능 향상은 확인하지 못했습니다. 따라서 후보 캐시는 테스트 전용 상태로 유지한다고 문서에 명시합니다.

이 결과가 중요한 이유는 기술적 선택을 성공담으로만 정리하지 않아도 되기 때문입니다. 캐시를 만드는 데 성공했지만, 실제 이점이 확인되지 않았다면 제품에 적용하지 않는 것도 올바른 결정입니다.

```sh
cargo test --release -p boundra-cli --test incremental-experiment -- --nocapture
```

실제 저장소에서 제공하는 실험 명령입니다. 이 글에서 새로 실행하거나 측정한 수치가 아닙니다. 실측 성능을 비교할 때에는 실행 환경, 파일 수, 최초/후속 실행, 반복 측정의 중앙값과 메모리 영향까지 구분해야 합니다.

테스트에서 두 결과가 같다고 판단하기 전에 어떤 값들을 비교하고 있는지 확인해야 합니다. 예를 들어 진단의 규칙 ID만 같고 실제 파일 위치가 달라졌다면 도구를 사용하는 사람에게는 다른 결과입니다. 비교 기준이 실제 공개 계약과 가까울수록 이후 내부 구현을 바꾸더라도 테스트를 유지하기 편해집니다.

## 자동 검사의 한계

컴포넌트 테스트는 브라우저의 폰트, 실제 레이아웃, 클립보드 권한과 스크롤 조건을 완전히 대체할 수 없습니다. 반대로 모든 순수 계산을 브라우저 테스트로 실행하면 비용과 실패 원인 추적이 어려워집니다.

검사 결과는 검증한 계약의 범위만 보장합니다. 예를 들어 실제 키보드 조작을 확인한 브라우저 테스트가 존재한다고 접근성 적합성을 전부 증명하는 것은 아닙니다. 브라우저별 차이와 자동 검사가 확인하지 못하는 사용 경험을 별도로 검증합니다.

## 빠른 테스트와 올바른 테스트

테스트를 빠르게 만들겠다고 검사 대상을 줄였다면 기존 검사와 같은 결과가 나오는지부터 확인해야 합니다. 전체 검사와 증분 검사를 비교하는 이유도 여기에 있습니다. 속도가 빨라졌다는 수치보다 기존에 발견하던 오류를 계속 발견하는지가 먼저입니다.
