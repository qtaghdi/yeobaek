## 클릭은 어떻게 이동할까?

버튼을 클릭했다고 해서 버튼에서만 이벤트를 처리하는 것은 아닙니다. 브라우저는 조상에서 대상으로 내려가는 캡처 단계, 대상 단계, 그리고 버블링하는 이벤트라면 다시 조상으로 올라가는 버블 단계의 순서로 이벤트를 전달합니다.

그래서 부모의 핸들러 안에서도 실제 클릭한 요소인 `event.target`과 현재 핸들러가 실행 중인 `event.currentTarget`이 서로 다를 수 있습니다.

같은 부모 요소에 capture 옵션이 있는 핸들러와 일반 클릭 핸들러를 모두 등록하면 서로 다른 시점에 호출되는 모습을 확인할 수 있습니다. 예를 들어 `parent.addEventListener("click", capture, true)`는 대상에 도착하기 전에, `parent.addEventListener("click", bubble)`은 버블링 단계에서 실행됩니다. 이벤트가 부모에서 시작된다는 뜻은 아닙니다. 실제 클릭 대상은 여전히 버튼이고, 호출되는 핸들러만 이벤트 경로에 따라 달라집니다.

## 전파를 막는 것과 기본 동작을 막는 것

`stopPropagation()`은 이후 전파를 차단하지만 기본 브라우저 동작을 막지 않습니다. `preventDefault()`는 취소 가능한 이벤트의 기본 동작을 막지만 전파는 계속될 수 있습니다.

예를 들어 링크를 누를 때 `preventDefault()`를 호출하면 링크 이동은 취소될 수 있지만 상위의 클릭 핸들러는 실행될 수 있습니다. 반대로 `stopPropagation()`만 호출하면 상위로 이벤트가 전달되지 않더라도 링크의 기본 이동은 취소되지 않습니다. 같은 대상에 등록된 다른 리스너까지 막는 것은 별개의 `stopImmediatePropagation()`입니다.

그렇다면 처음의 즐겨찾기 문제를 무조건 `stopPropagation()`으로 해결하면 될까요? 카드 안의 링크와 버튼을 형제 요소로 배치할 수 있다면 부모 핸들러에서 클릭 대상을 일일이 예외 처리하지 않아도 됩니다. 이벤트를 막기 전에 UI 구조부터 살펴볼 만한 이유입니다.

## 이벤트를 어디에서 책임질까?

Interaction Inspector의 요소 선택 모드에서도 페이지와 확장 UI의 이벤트를 구분해야 했습니다. [#26](https://github.com/Oddmash/interaction-inspector/issues/26)처럼 Escape를 처리하더라도 선택 중이 아닌 페이지의 정상 조작까지 바꾸지 않아야 합니다. 이벤트를 막기 전에 현재 어떤 기능이 이벤트를 소유하는지 먼저 생각해봅시다.
